\section{Executive assessment}

The most useful interpretation of AsymptoticAnalysis is an explicit algebra of asymptotic information, with several specialized inverse engines and an interoperability layer. A result can retain a finite expression, a scale, a remainder, branch information, a source model, and enough provenance to support later operations. The ordinary power--log representation is complemented by logarithmic, Fourier, Gamma/Barnes, flat-sector, and exact exponential-core constructions. This is a materially different objective from returning only a plausible leading expression. The public definitions and inspected specialized modules support this architectural reading \cite{core,fourier,gammainverse,expcore}.

The repository is also changing rapidly. Its review directory contains three waves of nine reports. The maintained registers explicitly distinguish current fixes from historical observations and unresolved proposals. The latest source already contains fixes and compatibility work absent from the third-wave snapshot. Consequently, a useful fourth inspection must not start by copying earlier complaints about dense \code{SeriesData}, captured assumptions, or missing CI. This report uses the implementation register and wave-three crosswalk as an exclusion map, then follows newer code paths \cite{reviewindex,status,intake}.

\textbf{The main new technical result is a more precise account of the Mathics boundary.} Inspection of Mathics 10.0.1 shows that its two-argument \code{ProductLog} problem is not adequately explained as a numerical mpmath argument swap. The exact-expression SymPy conversion also preserves the wrong argument order, while the inherited mpmath arity gate admits only one argument. These are different failure modes. The package's principal-branch construction-site workaround helps selected internal expressions but does not provide a general symbolic or numerical bridge \cite{mathicscorefunctions,upstreamexp,upstreambuiltin}.

Two additional compatibility gaps have small, exact repairs. The polynomial real-domain adapter requires numerically recognized real coefficients, even when a symbolic coefficient is proved real by the request's retained assumptions. The eventual-condition adapter tries only seven predetermined radii before falling back to a general quantifier mechanism. It therefore has no constructive route for a perfectly valid but sufficiently narrow neighborhood. A parameter-aware coefficient proof and a leading-coefficient radius certificate address these particular gaps without weakening mathematical admission \cite{mathicsbranches,inversebranches,inverseexpressions}.

The performance contribution is deliberately a delta to existing budget findings: \emph{sparse logarithmic coefficient polynomials can still be made dense inside the coefficient layer}. The Mathics \code{CoefficientRules} adapter constructs a full \code{CoefficientList}, and the common Fourier implementation also uses dense coefficient lists. Bounding source support or Fourier frequencies does not bound this work. The supplied sparse reference implementation operates on a two-term polynomial of degree $10^8$ without allocating $10^8+1$ coefficient positions. That is an independently executed representation test, not a native package benchmark \cite{mathicsalgebra,fourier}.

Finally, the portable runner's before/after source comparison is weaker than its natural-language interpretation: it detects unequal observed endpoint contents, not every change during execution. Its test script is frozen, but its package source is read from the original tree. An independently executed A--B--A countermodel establishes the distinction. The repository's own definition-comparison workflow already uses snapshots; the recommendation is to reuse that design, not invent another generic validation framework \cite{runner,compatibility}.

\section{Architecture and comparison with Wolfram Language}
\subsection{What the package actually contributes}

An ordinary power--log object represents a finite expression of the form
\begin{equation}\label{eq:ordinary}
 F(u)=\sum_{\beta<h}u^\beta P_\beta(\log u)
 +O\!\left(u^\rho(1+|\log u|)^k\right),\qquad u\downarrow0,
\end{equation}
with exact real exponents and polynomial logarithmic coefficients. The local coordinate can encode a finite endpoint and side, or a signed infinity. The core exports terms, remainder metadata, an ordinary expression, and model/provenance information. Specialized engines change the scale rather than pretending that every expression lies on a single rational-power lattice \cite{core,fourier,gammainverse,expcore}.

This information is useful only when preserved under operations. Addition, multiplication, logarithms, powers, composition, observables, truncation, refinement, and qualified differentiation are exposed as explicit operations; ordinary arithmetic is also routed through the object interface. Differentiation is not justified from a magnitude bound alone: the public contract asks for matching derivative information. Inverse residuals distinguish a finite-model identity from an interval certificate for an actual numerical root. These distinctions are strengths worth retaining during compatibility work \cite{core,status}.

The Fourier layer adds a second algebra inside each source-power block:
\begin{equation}\label{eq:fourier}
 P_\beta(L)=\sum_{\omega\in\Omega_\beta}Q_{\beta,\omega}(L)e^{i\omega L},
 \qquad L=\log u.
\end{equation}
It explicitly tracks frequencies and their real-conjugacy relation. The Gamma/Barnes inverse layer instead organizes complete inverse-logarithmic polynomials around an exact Lambert core. The exponential-core layer can retain an exact inverse while expanding perturbative sectors around it. A correct implementation must preserve both the outer grading and the inner coefficient algebra; the latter becomes central to D-P06 \cite{fourier,gammainverse,expcore}.

\subsection{Compare equal mathematical requests}

The ordinary package cutoff retains exponents strictly below $h$. Native \code{Series} uses its own order convention. For the mathematical expansion of $e^x$, a package cutoff of three requests
\[
 1+x+\tfrac12x^2+O(x^3),
\]
whereas native integer order three includes the cubic term. The appropriate ordinary comparison is therefore with native order two, subject to the chosen approach and remainder contract. These are specification examples, not printed outputs obtained in this review \cite{core,wlseries}.

A second comparison dimension is the exponent set. Let $\alpha>1$ be fixed and real, and solve $y=x+x^\alpha$ on the positive germ. Writing $x=yv$ and $z=y^{\alpha-1}$ gives
\[
 1=v+zv^\alpha.
\]
Coefficient matching at $v=1$ yields
\begin{equation}\label{eq:irrational}
 x=y-y^\alpha+\alpha y^{2\alpha-1}
 -\frac{\alpha(3\alpha-1)}2y^{3\alpha-2}+\cdots.
\end{equation}
For $\alpha=\sqrt2$, these exponents are not a single fixed rational \code{SeriesData} lattice in $y$. This explains the utility of a generalized representation. It does \emph{not} establish that native \code{Asymptotic} or \code{AsymptoticSolve} cannot obtain such an approximation. The mathematical derivation and the representation comparison are separate claims \cite{wlseriesdata,wlasymptoticsolve}.

Similarly, retaining an exact core can be useful even when an elementary or Lambert expression is already known. It prevents an outer perturbation expansion from repeatedly re-expanding that core. In exchange, later numerical evaluation inherits the runtime's ability to interpret that exact expression correctly. The expression \emph{looks} portable while its evaluator may not be; M01 concerns precisely this boundary.

\subsection{Native delegation is not interpreter substitution}

The current public API includes explicit \code{"Series"}, \code{"Asymptotic"}, and \code{"Package"} backend choices and automatic routing. Native results retain a distinct kind/scale and do not acquire an analytic package remainder merely because a native computation returned an expression. Automatic routing already exists; claims from older reviews that all delegation must be explicit are obsolete for this snapshot \cite{core,status}.

On Mathics, selecting a native backend selects Mathics's implementation, not the official Wolfram implementation. Creating an inert \code{System`} name permits parsing and symbol agreement but supplies no solver. Thus even a complete dispatcher cannot, by itself, satisfy the goal of subsuming every successful official-kernel input on another interpreter. The actual computational or theorem-producing capability has to be implemented, delegated to a genuinely available service, or truthfully reported as unavailable \cite{compatibility,mathicscompat}.

\section{Mathics compatibility: present strengths and evidence limits}
\subsection{The isolation design is appropriate}

The package does not indiscriminately replace global \code{System`} definitions. Its compatibility modules are loaded conditionally and use a package-owned context; the ordinary Wolfram path keeps its own bindings. The Mathics bootstrap creates selected inert public-input names so that option and function symbols agree across caller and package contexts. This is a sensible compromise between parser compatibility and evaluator substitution, provided that symbol existence is never used as proof of implementation \cite{mathicscompat,compatibility}.

The adapters are more substantive than a collection of aliases. They address explicit Module-targeted returns, held extraction for named functions, association access and updates, empty-list mapping, exact realness/sign consequences, finite defining Taylor expansions, Stirling modeling, formatting installation, and interpreter-specific deadlines. Several comments carefully distinguish a conservative unknown answer from a proof. In particular, the current assumption layer checks the realness of operands before permitting native simplification of ordered predicates; this avoids manufacturing a real inequality by canceling a common complex offset \cite{mathicscompat,mathicscalls,mathicslists,mathicsassumptions,mathicssimplification,mathicstaylor,mathicsspecial}.

These are good boundaries to preserve. Replacing them with aggressive \code{PowerExpand}, numerical sampling, or global built-in patches would trade visible coverage gaps for difficult-to-audit incorrect results. The repairs proposed below add narrowly scoped mathematical facts rather than weaken the existing admission policy.

\section{M01: ProductLog has more than one compatibility failure mode}\label{sec:m01}
\evidence{S/D/E/U. The source mapping and arity facts are directly inspected. The numerical examples in this section were executed independently in SymPy/mpmath. No output is attributed to a running Mathics or AsymptoticAnalysis instance.}

\subsection{The mathematical and interchange contracts}

Write $W_k(z)$ for branch $k$ of the Lambert function, so that
\begin{equation}\label{eq:lambertidentity}
 W_k(z)e^{W_k(z)}=z.
\end{equation}
Wolfram's two-argument spelling is \code{ProductLog[k,z]}. The corresponding SymPy constructor uses the argument first, \code{LambertW(z,k)}. A bridge must therefore preserve branch identity while exchanging positions in both conversion directions. A principal one-argument form can be normalized separately. The bundled reference conversion implements that contract, rather than calling the two constructors with the same positional list \cite{upstreamexp,upstreambuiltin}.

The current package comments attribute the Mathics two-argument problem to forwarding Wolfram-order arguments to mpmath. Following the upstream implementation gives a sharper diagnosis. The Mathics \code{ProductLog} class inherits its exact conversion behavior from \code{SympyFunction}; the default \code{prepare_sympy} does not reorder the operands. The exact evaluation route calls that conversion before converting a result back. Meanwhile, the inherited \code{MPMathFunction} default declares \code{nargs = \{1\}}; the \code{ProductLog} class does not override it to admit two numerical arguments \cite{mathicscorefunctions,upstreamexp,upstreambuiltin}.

Thus there are at least three distinct contracts to test: exact conversion, conversion back after symbolic transformations, and inexact numerical evaluation. A claim about one is not evidence for the other two.

\subsection{An exact countermodel and a numerical non-conclusion}

The principal identity $W_0(e)=1$ gives an especially small countermodel. An unreordered exact bridge sends \code{ProductLog[0,E]} to \code{LambertW(0,E)}, not to \code{LambertW(E,0)}. The independent SymPy evaluation recorded in the archive is
\[
 \operatorname{LambertW}(e,0)=1,
 \qquad \operatorname{LambertW}(0,e)=-\infty.
\]
The second expression is the bridge countermodel, not a legitimate interpretation of the requested Wolfram expression.

It would nevertheless be wrong to infer that every inexact two-argument Mathics call necessarily takes the same bad numerical route. The inspected mpmath arity check can reject the two-argument call and leave it unevaluated. This matters operationally: ``wrong value,'' ``wrong exact simplification,'' and ``inert expression'' need different regression expectations and fixes. The earlier package comment does not capture that distinction \cite{upstreambuiltin,upstreamexp}.

A no-op symbolic round trip can also be misleading. If both directions preserve the same wrong ordering, an uninterpreted pair may come back looking unchanged. That does not prove that simplification or numerical specialization used the intended function in the intermediate representation. Acceptance tests must examine the \emph{intermediate semantics}, not only structural equality before and after a round trip.

\subsection{What the current workaround covers}

The package's late Mathics helper normalizes branch zero to the one-argument System form, while nonzero branches are passed through. A definition rewrite applies the helper at four named construction sites: automatic core inversion, exponential-core exact inversion, Lambert construction, and special thresholds. The code is intentionally isolated and avoids changing global System definitions \cite{mathicscorefunctions}.

This improves those internal principal constructions. It is not a parser-wide interception of every \code{ProductLog[0,z]} supplied by a caller, nor a numerical implementation of $W_{-1}$. A held public constructor eventually evaluates source expressions in its private entry path. The following supplied characterization compares mathematically equivalent source constants:
\begin{lstlisting}
AsymptoticExpansion[x + ProductLog[0, E], {x, 0, 3},
  "Backend" -> "Package"]
AsymptoticExpansion[x + ProductLog[E], {x, 0, 3},
  "Backend" -> "Package"]
\end{lstlisting}
The mathematically correct finite expression is $1+x$. Whether the first call is rejected after native pre-evaluation, remains unresolved, or is normalized elsewhere is an integration observation still to be made. The probe is not accompanied by fabricated package output.

\subsection{A nonprincipal exact-core witness}

Consider
\[
 f(x)=\frac{e^x}{x},\qquad x>1.
\]
Its derivative is $e^x(x-1)/x^2>0$, and the increasing inverse is
\begin{equation}\label{eq:minusonecore}
 g(y)=-W_{-1}(-1/y),\qquad y>e.
\end{equation}
At $y=e^2/2$, the correct value is exactly $2$. The inspected exponential-core constructor selects branch $-1$ when its power parameter $b$ is negative; $e^x/x$ is the case $a=c=p=1$, $b=-1$. With zero perturbation, retaining this exact core is mathematically appropriate \cite{expcore}.

The generalized-series numeric accessor, however, performs direct substitution into the stored expression outside the Native kind. It has no interpreter-specific nonprincipal Lambert guard \cite{core}. This creates a concrete boundary to characterize:
\begin{lstlisting}
s = AsymptoticExponentialCoreInverse[
  Exp[x]/x, 0, {x, Infinity}, {y, 0}];
{Normal[s], s[N[E^2/2, 30]]}
\end{lstlisting}
The source and mathematics establish what must be preserved. They do not establish the exact current Mathics printout. For illustration only, independently evaluating the \emph{swapped SymPy expression}
\[
 -\operatorname{LambertW}(-1,-2/e^2)
 \approx 0.3181315052-1.3372357014\,i
\]
gives neither the correct branch nor the correct real value. This is recorded as a SymPy countermodel, explicitly \emph{not} as observed package output.

\subsection{Repair and acceptance obligations}

The durable fix belongs at the upstream interchange boundary: convert \code{ProductLog[k,z]} to \code{LambertW(z,k)}, invert that transformation when returning, admit the numerical arities actually supported, and validate the branch argument rather than allow it to be confused with the evaluation point. Principal and nonprincipal tests must cover exact input, arbitrary-precision input, symbolic transformations, and numerical specialization after storage. Fixing only one conversion direction is insufficient.

For the package, an interim repair should remain package-owned. A narrowly admitted literal principal-branch form can be normalized while the source is held, before ordinary evaluation. Nonprincipal symbolic expressions can remain available where their manipulation is proved safe, but a package numerical operation must either use a tested bridge or return a clear capability refusal. This is not a proposal to globally patch Mathics's System function. A general unchecked external operation on \code{Normal[s]} cannot be made safe solely by guarding \code{s[value]}; that limitation should remain explicit.

Acceptance requires the principal control above, the exact-core point $2$, branch-$-1$ fixed-point residuals at several negative arguments in $(-1/e,0)$, and symbolic round trips that inspect branch positions. Near the branch point, numerical conditioning deserves a separate tolerance policy. A value with a small residual alone is not a proof that the desired branch was selected.

\section{M02: retained assumptions stop before polynomial-domain inference}\label{sec:m02}
\evidence{S/D/E/U. The missing assumption argument is visible in the adapter. Exact monotonicity and inverse-coefficient checks were run independently; the public callable comparison remains unrun.}

\subsection{The missing parameter}

The Mathics polynomial-domain helper proves that a polynomial with numerically recognized exact real coefficients has domain all of $\mathbb R$. Its coefficient condition uses the core's \code{exactRealQ}, which includes \code{NumericQ}. It takes three arguments: body, source symbol, and Reals. The late rewrite substitutes this helper for \code{FunctionDomain} inside branch selection \cite{mathicsbranches,core}.

The branch-selection routine itself has access to the request's retained assumptions. The helper does not receive them. A symbolic coefficient $a$ therefore does not become admissible merely because the request states $a>0$. This is not the old ambient-assumption leakage problem: assumptions can be properly retained at the object/request boundary and still be unavailable at a particular proof call. The specific defect is an overly restrictive proof interface \cite{inversebranches,status}.

\subsection{A complete mathematical oracle}

Let $a>0$ and
\begin{equation}\label{eq:cubic}
 f_a(x)=ax+x^3.
\end{equation}
Every coefficient is real, the polynomial is defined for all real $x$, and
\[
 f_a'(x)=a+3x^2>0.
\]
Together with its limits at $\pm\infty$, this gives a unique increasing real inverse. Around zero it has
\begin{equation}\label{eq:cubicinverse}
 g_a(y)=\sum_{n\ge0}
 \frac{(-1)^n}{(2n+1)a^{3n+1}}\binom{3n}{n}y^{2n+1}.
\end{equation}
For completeness, apply ordinary Lagrange inversion to $y=x(a+x^2)$. The coefficient of $y^m$ is $m^{-1}[x^{m-1}](a+x^2)^{-m}$. Odd $m=2n+1$ gives
\[
 \frac1{2n+1}a^{-(2n+1)}a^{-n}
 \binom{-2n-1}{n}
 =\frac{(-1)^n}{(2n+1)a^{3n+1}}\binom{3n}{n};
\]
even coefficients vanish. In particular,
\[
 g_a(y)=\frac ya-\frac{y^3}{a^4}+\frac{3y^5}{a^7}
 -\frac{12y^7}{a^{10}}+\frac{55y^9}{a^{13}}+\cdots.
\]
The independent test substitutes this polynomial into $ag+g^3-y$ and verifies cancellation through degree ten. The analytic inverse exists near zero because $f_a'(0)=a\ne0$; the series is not being asserted uniformly as $a\downarrow0$.

\subsection{The public comparison and the appropriate repair}

The supplied probe compares an inverse callable passed to forward expansion with the direct inverse constructor:
\begin{lstlisting}
AsymptoticExpansion[InverseFunction[Function[t, a t + t^3]],
  {y, 0, 6}, Assumptions -> a > 0, "Backend" -> "Package"]
AsymptoticInverse[a x + x^3, {x, 0}, {y, 6},
  Assumptions -> a > 0]
\end{lstlisting}
Native pre-evaluation of \code{InverseFunction} can differ between runtimes, as the repository already documents. The test must therefore retain the original call and classify whether the specialized branch path was actually reached. The source finding does not assume that every syntactic form produces the same failure message \cite{callables,inverseexpressions}.

A suitable replacement hook takes the assumptions explicitly:
\begin{lstlisting}
polynomialRealDomain[body, source, assumptions]
\end{lstlisting}
It should first establish polynomiality in the source variable, then prove each coefficient finite real under parameter-only assumptions. If any coefficient proof remains unknown, the result remains unknown. If the body is not polynomial, the existing general fallback remains available. No ambient default should silently strengthen the retained domain.

The companion \code{PolynomialRealDomain} prototype follows this design and uses the supplied sparse coefficient extractor. It returns \code{True} only on proof and \code{None} otherwise. It has not been run in either Wolfram or Mathics and is not installed by the archive. The Python oracle verifies the mathematical example, not that prototype's evaluator behavior.

The minimum acceptance set is $a>0$, $a\in\mathbb R$ for domain-only inference, no assumptions, an explicitly nonreal coefficient, and a parameter that depends on the source. Domain inference and monotonicity must remain separate: proving $a\in\mathbb R$ makes \eqref{eq:cubic} real everywhere but does not prove that it is globally increasing for every such $a$.

\section{M03: replace fixed radius guesses by a constructive witness}\label{sec:m03}
\evidence{S/D/E/U. The seven-trial schedule is inspected. The radius theorem is proved below, with 400 exact polynomial cases and additional targeted checks in the independent test suite. No general Mathics quantifier fallback was executed here.}

\subsection{Why seven radii cannot establish eventual completeness}

The Mathics replacement for \code{inverseFunctionEventually} simplifies under $u>0$, then tries affine interval proofs at
\[
 1,\frac12,\frac14,\ldots,\frac1{64}.
\]
If no trial succeeds, it invokes the original eventual-condition mechanism. That original path asks for an existential positive radius and a universal condition throughout the resulting deleted neighborhood, using general symbolic quantifiers. Those facilities are not supplied by the bounded affine adapter \cite{mathicsbranches,inverseexpressions}.

For the condition $u<1/1000$, every listed radius extends beyond the valid interval. The correct affine interval answer at each of those radii is inconclusive, not true. Nevertheless, the condition holds for every sufficiently small positive $u$. The same issue occurs at arbitrarily small rational margins and, more importantly, for the parameterized condition $u<\eta$ under $\eta>0$: no single fixed trial radius works for every admitted parameter value.

The following public source pair has the same local germ and different distant cutoffs:
\begin{lstlisting}
AsymptoticExpansion[ConditionalExpression[x, x < 1/1000],
  {x, 0, 3}, "Backend" -> "Package"]
AsymptoticExpansion[ConditionalExpression[x, x < 1],
  {x, 0, 3}, "Backend" -> "Package"]
\end{lstlisting}
Both are mathematically the identity near zero from above. The bounded trial mechanism can prove the second condition at radius one but not the first at any of its seven radii. Whether some other runtime simplification discharges the first call is left to the supplied integration probe. The independent oracle models only the explicit seven trials and labels that scope in its docstring.

\subsection{An exact polynomial radius certificate}

The gap does not require a general quantifier-elimination implementation. A small leading-coefficient theorem suffices for polynomial predicates.

\begin{proposition}[Constructive eventual sign]\label{prop:radius}
Let $P\in\mathbb R[u]$ be nonzero, and write
\[
 P(u)=u^m\left(c+\sum_{j>m}c_j u^{j-m}\right),\qquad c\ne0,
\]
where $m$ is the least retained exponent. Set
\begin{equation}\label{eq:radius}
 B=\sum_{j>m}|c_j|,\qquad
 r=\min\left(1,\frac{|c|}{2(1+B)}\right).
\end{equation}
Then $r>0$, and $P(u)$ has the sign of $c$ throughout $0<u<r$.
\end{proposition}
\begin{proof}
For $0<u<r\le1$ and each integer $j-m\ge1$, one has $u^{j-m}\le u$. Hence
\[
 \left|\sum_{j>m}c_j u^{j-m}\right|\le uB<\frac{|c|}{2}
\]
when $B>0$, using $rB\le |c|B/(2(1+B))<|c|/2$. For $B=0$ the tail vanishes. The bracket cannot change the sign of $c$, and $u^m>0$ on the stated interval.
\end{proof}

All quantities can remain exact. For $P(u)=1/1000-u$, the formula gives $r=1/4000$, immediately certifying a positive neighborhood. It is intentionally conservative; it is a proof-producing bound, not an attempt to compute the maximal interval. Very small leading coefficients affect the size of the exact rational radius, not the number of trial guesses.

For symbolic coefficients, the same formula is valid under retained assumptions that prove the relevant coefficients real and the leading coefficient nonzero with a determined sign. The returned radius may depend on parameters. This proves a pointwise family of eventual statements, not a uniform radius or uniform asymptotic constant across the parameter domain. If the leading coefficient might vanish, the helper must return unknown or perform an independently justified case split.

\subsection{Relations, conjunctions, and ordered domains}

Apply Proposition~\ref{prop:radius} to the difference of the two sides of a binary polynomial relation. Positive, negative, and identically zero differences determine the eventual truth of $<,\le,>,\ge,=,\ne$. A conjunction of certified predicates is certified on the minimum of their positive radii. An ordered chain is treated through its adjacent comparisons; an all-distinct predicate requires all pairs, not merely adjacent pairs.

For an \emph{ordered} relation, both original operands must first be proved real in the local domain. Proving only that their difference is real is not enough. For example, canceling a common imaginary offset does not turn an order comparison of complex values into an admitted real inequality. The repository already guards this issue in its assumption and affine-interval adapters; the proposed certificate must retain that guard \cite{mathicsassumptions,mathicsbranches,mathicssimplification}.

The zero polynomial is handled separately and has no leading nonzero coefficient. Unknown symbolic cancellation is likewise not permission to delete a coefficient. In a bounded implementation, inability to establish the leading term produces an unresolved proof request, not a guessed sign.

\subsection{A crucial integration distinction: eventual is not fixed-interval}

There are two different questions in the branch code:
\[
 \exists r>0\;\forall u\in(0,r):C(u),
 \qquad\text{and}\qquad
 \forall u\in(0,r_0):C(u)
\]
for a \emph{previously chosen} $r_0$. The new radius certificate answers the first. It may answer the second only if the returned witness is at least $r_0$, or after the surrounding algorithm explicitly shrinks its recorded domain and propagates that change.

For instance, $1-1000u>0$ is eventually true but not true throughout $(0,1)$. It would be unsound to replace the fixed-interval \code{inverseBranchEventualQ} by a Boolean eventual test and keep the old radius metadata. The independent suite includes this counterexample specifically to prevent an attractive but incorrect patch.

The simplest integration is therefore to use the new result first in \code{inverseFunctionEventually}, whose contract is genuinely existential. A later integration into branch-validation intervals should return a certificate containing the actual radius and update all dependent interval statements. This scope distinction is more important than making the radius numerically sharp.

\subsection{Implementation and test boundary}

The Python implementation supports sparse polynomials with exact rational coefficients and returns a structured certificate with the sign, radius, valuation, leading coefficient, and coefficient majorant. Its verifier checks the stated sufficient inequality. The Wolfram Language companion is intentionally narrower: it prototypes binary affine comparisons with explicit assumptions. It is not a complete implementation of arbitrary polynomial or Boolean predicates.

The executed evidence consists of exact narrow-margin examples, margins down to $2^{-1000}$ in the targeted affine tests, 400 deterministic random polynomial cases, three exact interior evaluations per random case, and majorant verification. Sampling alone would not prove the proposition; the proof above supplies that justification, while the exact evaluations help detect implementation mistakes. The code keeps a crossing predicate's fixed-interval answer distinct from a universally false predicate.

\section{D-P06: sparse outer jets can hide dense inner polynomials}\label{sec:sparse}
\evidence{S/D/E/U. The dense calls are inspected. Storage-position counts are exact consequences of the representations. The sparse reference algorithms were executed; no native timing, peak-memory measurement, or large-degree package stress run is claimed.}

\subsection{A separate allocation dimension}

Let
\[
 Q(L)=1+L^D.
\]
This polynomial has two nonzero coefficients, but a degree-indexed coefficient list has $D+1$ positions. The distinction remains even if an implementation shares its zero objects: the list still needs $D+1$ indexed positions. The degree $D$ itself takes only $O(\log D)$ bits to encode.

The Mathics \code{CoefficientRules} adapter currently obtains its result by expanding the polynomial, constructing \code{CoefficientList}, pairing every position with its degree, and discarding zero entries. The final answer is sparse, but the intermediate representation is not. For this example, producing two rules passes through a degree-sized array \cite{mathicsalgebra}.

The same dimension exists outside the Mathics-only layer. The common Fourier routine \code{fourierPoly} canonicalizes all entries of a \code{CoefficientList} and reconstructs the polynomial using powers indexed by the degree range. \code{fourierEnvelope} also enumerates a coefficient list. Thus the issue is not fixed by making the Mathics primitive sparse while leaving the Fourier consumer unchanged \cite{fourier}.

\subsection{Why the public budgets do not control it}

Equation~\eqref{eq:fourier} has at least three distinct sizes: the number of source weights $\beta$, the number of frequencies $\omega$, and the support/degree of each $Q_{\beta,\omega}$. A source with few weights and two frequencies can still have an enormous logarithmic degree. A candidate family is
\begin{equation}\label{eq:fourierstress}
 f_D(x)=x+x^2(\log x)^D\sin(\log x),\qquad x\downarrow0,
\end{equation}
where $D$ is a fixed nonnegative integer. For every fixed $D$, $x(\log x)^D\to0$, so the correction is asymptotically smaller than the leading $x$. Differentiating the correction shows a factor $x$ times a finite logarithmic polynomial/trigonometric expression, so the derivative tends to one. An increasing local inverse exists sufficiently near zero.

This family therefore tests a legitimate input dimension rather than merely a malformed expression. Parsing its trigonometric coefficient produces two frequency modes with high-degree polynomial amplitudes. A small \code{MaxFrequencies} does not bound $D$, and a bound on retained source blocks does not either. The relevant package entry for a bounded characterization is
\begin{lstlisting}
AsymptoticFourierInverse[
  x + x^2 Log[x]^D Sin[Log[x]], {x, 0}, {y, 3},
  "MaxTerms" -> 20000, "MaxFrequencies" -> 256]
\end{lstlisting}
No claim is made that this call was executed or that it reaches the same final failure on every runtime. A regression should start at modest degrees and measure the parsing/canonicalization phase separately. Running an enormous $D$ against the current dense implementation is not necessary to establish the allocation mechanism.

There is also a narrower consumer optimization. \code{gammaInverseBound} calls \code{CoefficientRules} to obtain the smallest nonzero inverse-logarithmic exponent. It needs a valuation, not a full degree-indexed list. That call should be implemented as a direct sparse valuation query. This does not imply that the current Gamma constructor cheaply reaches degree $10^8$; its preceding coefficient-generation work has its own cost. The call identifies unnecessary representation work, not a demonstrated end-to-end Gamma benchmark \cite{gammainverse}.

\subsection{A sparse alternative and its real cost model}

Store a polynomial as a sorted collection
\[
 \{(d_j,c_j):j=1,\ldots,s\},\qquad 0\le d_1<\cdots<d_s,\quad c_j\ne0.
\]
Coefficient rules and valuation then read this support directly. Differentiation maps $(d,c)$ to $(d-1,dc)$ for $d>0$. An $\ell^1$ envelope is the expression
\[
 \sum_j |c_j|M^{d_j},
\]
which does not require inserting interior zeros. Addition merges equal degrees; multiplication convolves pairs with an explicit candidate-pair budget. Canonicalization of coefficients and equality grouping still need their own proof/cost policies.

For fixed coefficient bit-size, storing the support takes $O(s\log D)$ degree bits rather than $D+1$ positions. This is a representation statement, not a universal runtime bound. Expansion of a factored expression can increase $s$ dramatically, and coefficient simplification can dominate. A sparse extractor should therefore be paired with an input-expansion budget or a representation-aware traversal; merely replacing one list constructor does not solve all expression swell.

The supplied Python helper avoids a subtle trap in an independent oracle: it does not construct a SymPy \code{Poly} for the huge-degree case. Instead, after expansion, it reads monomial degree/coefficient pairs and rejects residual dependence on the selected variable. The separate exact-rational \code{SparsePolynomial} class has immutable sorted support, validation, cancellation, differentiation, multiplication, and valuation operations. The Wolfram Language companion provides the corresponding bounded extraction design but remains unrun.

A patch should first replace the new Mathics primitive and the specific Fourier consumers, then verify coefficients, frequency conjugacy, zero-polynomial behavior, and remainder-envelope equivalence at ordinary degrees. \section{D-V01 and T01: what a portable test receipt can prove}\label{sec:receipt}
\evidence{S/D/E/U. The portable runner was read, but not launched with a native kernel. A source-mutation countermodel and the supplied patch/archive helper tests were executed independently.}

\subsection{The current runner has important safeguards}

The portable Python runner uses fresh processes, validates declared case IDs, rejects an empty selection, and distinguishes explicit success/failure records from crashes, timeouts, launch errors, and protocol errors. It retains complete diagnostics. Its timeout handling terminates the owned process group or Windows process tree, rather than indiscriminately killing all kernel processes. It also freezes the Wolfram Language test script to avoid a streamed input file changing underneath an interpreter \cite{runner}.

These are strong improvements over the legacy aggregate-runner concerns in older reviews. The problem below is narrower: it concerns what the source-integrity field means, not whether every test result can be trusted or whether the runner has no safeguards.

\subsection{Endpoint observations do not establish temporal immutability}

The runner computes fingerprints before execution and when it writes reports. It passes the original resolved package path to the test through an environment variable. Its frozen test script is therefore not paired with a frozen package tree. The field \code{SourcesUnchangedDuringRun} is calculated by comparing observed before/after contents \cite{runner}.

Consider an ordinary file with initial contents A. Between two observations it is changed to B, the interpreter reads B, and the file is restored to A. The endpoint contents compare equal, yet the interpreter did not consume A. This requires no hash collision and no exotic filesystem semantics. It is simply a different temporal proposition:
\[
 \text{contents at }t_0=\text{contents at }t_1
 \quad\not\Rightarrow\quad
 \text{contents were constant on }[t_0,t_1].
\]
The independent countermodel performs exactly these writes and reads, then records two Boolean facts: endpoint equality is true, and the read bytes differ from the initial bytes. It does not allege that such a change occurred in a repository acceptance run.

The distinction also matters without intentional interference. An editor, generator, checkout, or development script can change and restore files while a streamed load is in progress. A record should not promise a stronger invariant than the acquisition method supplies.

\subsection{Reuse an existing solution rather than invent another framework}

The repository's Mathics definition-comparison documentation already describes copying package inputs and capture scripts to temporary snapshots, checking their identities, and rejecting changes. The portable runner should reuse that acquisition boundary. At minimum it should distinguish ``original source contents matched at observations'' from ``these frozen inputs were executed'' \cite{compatibility}.

The companion characterization runner reads a resolved Git commit with \code{git archive}, extracts only ordinary files into a private temporary directory, copies the probe there, and loads the archived entry point. It supports both modular and standalone forms. This produces a coherent committed source snapshot and avoids pretending to test uncommitted working-tree edits. It is not a sandbox against hostile code running under the same operating-system account, and the report does not describe the temporary files as cryptographically immutable.

For production validation of working-tree changes, a coherent snapshot can be taken after generation, verified against the requested candidate, and then used exclusively by the kernel. The receipt should identify that snapshot and its selected tests. Native definition equality, a selected runtime regression, and a full-suite run should remain distinct record types. The current compatibility document already makes that distinction well.

\section{Two bounded extension and semantic items}
\subsection{L01: the Limit adapter silently chooses a side}\label{sec:limit}
\evidence{S/D/U. A helper-level semantic mismatch is identified. Inspected branch calls specify their side explicitly, so this report does not claim a current public wrong expansion.}

The Mathics Limit adapter translates direction strings to the corresponding signed integer forms, but maps \code{Automatic} to $+1$, the from-below direction. The current official documentation describes the ordinary default as a real two-sided limit. These contracts differ \cite{mathicssimplification,wllimit}.

The simplest mathematical separator is
\[
 \lim_{u\uparrow0}\frac{|u|}{u}=-1,
 \qquad
 \lim_{u\downarrow0}\frac{|u|}{u}=1.
\]
There is no common two-sided limit. A default mapped to $+1$ therefore cannot serve as a general emulation of the current native default.

This is a latent issue because the inspected branch validator passes \code{Direction -> -1} in its positive local coordinate. That call is not affected by the default mismatch \cite{inversebranches}. A safe repair is either to make the private adapter require an explicit side, or to implement a two-sided request by proving agreement of both admitted one-sided limits. It should not simply rename a one-sided result ``Automatic.'' Acceptance should include unequal sides, equal finite sides, and unresolved sides, while preserving the explicit branch controls.

This item should remain below the current branch/observable correctness obligations in priority. Its value is preventing a helper with broader-looking syntax from becoming an unsafe future dependency.

\subsection{G01: terminating hypergeometric polynomials need no convergence gate}\label{sec:hypergeom}
\evidence{S/D/E/U. The adapter gate and finite example are established. The interpreter may pre-evaluate a terminating example before the adapter sees it; no universal public failure is alleged.}

The defining-Taylor helper admits a restricted monomial argument, real upper parameters, positive lower parameters, and $p\le q+1$ for a generalized ${}_pF_q$. That inequality supplies a nonzero convergence radius for the admitted nonterminating series. However, a nonpositive integer upper parameter can terminate the series even when $p>q+1$; the resulting polynomial does not need that convergence condition \cite{mathicstaylor,dlmf16}.

For example,
\begin{equation}\label{eq:3f1}
 {}_3F_1\!\left(\begin{matrix}-2,3,4\\5\end{matrix};z\right)
 =1-\frac{24}{5}z+8z^2.
\end{equation}
The coefficient at degree one is $(-2)(3)(4)/5=-24/5$. The degree-two coefficient is
\[
 \frac{(-2)_2(3)_2(4)_2}{(5)_2\,2!}
 =\frac{2\cdot12\cdot20}{30\cdot2}=8,
\]
and all later terms vanish. At $z=2u^3$ the polynomial becomes
\[
 1-\frac{48}{5}u^3+32u^6.
\]
Both identities are independently checked in the archive.

A narrow extension should detect exact terminating upper parameters \emph{before} rejecting $p>q+1$. It can retain the current positive-lower-parameter restriction initially, avoiding ambiguous denominator zeros and cancellation conventions. The smallest terminating index gives a finite coefficient budget. If the requested cutoff excludes part of the polynomial, the returned approximation still has a nonzero omitted tail; exactness is justified only when all nonzero terms have been retained or the remainder is otherwise proved zero.

The distinction between helper coverage and public behavior is important. A native simplifier might already reduce \eqref{eq:3f1} to a polynomial, allowing the ordinary package path to succeed. In that case the public probe is a control, not evidence that the helper admits the original special-function syntax. The extension should be tested at its own admission boundary as well as through the public constructor.

This is an implementation opportunity within the existing finite-defining-series design, not an invitation to expand divergent nonterminating ${}_pF_q$ expressions as convergent Taylor series. No new asymptotic theorem is needed for the terminating polynomial.

A parameter-aware polynomial-domain helper needs an unproved-complex coefficient control. A constructive radius helper needs a fixed-interval crossing control. A terminating hypergeometric extension needs a nonterminating $p>q+1$ refusal. A Lambert numeric bridge needs the wrong-branch control even when a fixed-point residual is small.

For performance, add a third dimension: vary the resource that the fix addresses while keeping unrelated structure fixed. The D-P06 benchmark should hold source weights and frequencies fixed while increasing logarithmic degree. Varying all three together cannot show that the dense-inner-polynomial bottleneck was removed. Record construction, first access, and repeated access separately where result caching or display can move work between phases.

The native-preservation comparison should remain part of every adapter change. Context-local design reduces the risk of changing official-Wolfram behavior, but the late definition rewrites and generated standalone order are still executable code. Source equality of selected definitions is useful evidence; it is not a substitute for the new behavior-specific regressions.

\section{Conclusions}

AsymptoticAnalysis is a substantial mathematical software project with more structure than a front end to native expansion commands. Its strongest design choices are explicit scales, complete coefficient blocks, retained real-branch information, conservative remainder handling, and a separation between formal residuals, numerical evidence, and interval certificates. Wolfram Language nevertheless supplies broader native asymptotic facilities; a fair comparison treats those as real competitors and interoperability targets, not as absent functionality \cite{core,wlasymptotic,wlasymptoticsolve,wldiscrete}.

The inspected Mathics effort is serious and appropriately isolated. It now has dedicated adapters, tests, documentation, and CI. Full compatibility remains a goal rather than an established result. In particular, exact expression interchange, parameter-aware proof interfaces, and numerical branch evaluation require separate evidence. A successful load or an unchanged symbolic printout does not prove those contracts \cite{compatibility,mathicsci,mathicscorefunctions}.

The most actionable additions are therefore narrow: repair the ProductLog interchange boundary; pass retained assumptions into polynomial-domain inference; construct a real neighborhood witness instead of trying seven absolute scales; keep coefficient polynomials sparse in their own grading; and make test-source acquisition match the claim made by its receipt. The Limit-default and terminating-hypergeometric items are useful bounded follow-ons.

The supplied article and artifacts provide exact mathematical acceptance targets and reproducible independent checks for these changes. They do not claim that the proposed WL helpers are merged, that the public probes have passed, or that any old ledger item is closed by unrelated tests. That separation is necessary for the next implementation step to improve both capability and trustworthiness.
