This review examines the repository after its third intake of external code reviews and the introduction of substantial Mathics-specific compatibility machinery. Its principal new executable results concern the portable validation runner: an observed source change can be forgotten after restoration, and relocated modular sources can escape dependency monitoring. Both mechanisms are reproduced against the pinned upstream Python runner, with a deliberately synthetic kernel protocol; they are not claimed as Wolfram or Mathics package runs. A small patch is tested for the first defect.

The review also traces a remaining lower-Lambert-branch evaluation risk, identifies sparse-to-dense work in a Mathics algebra adapter, and characterizes a private limit-direction mismatch. Constructive artifacts include immutable Git-source staging, exact rational enclosures for the increasing inverse of $e^x/x$, and hypergeometric Taylor models with negative nonintegral denominator parameters and proved tail bounds. \section{Executive assessment}

AsymptoticAnalysis is most valuable as an explicit, inspectable calculus of selected asymptotic germs, not as a new name for ordinary power series. It combines exact real weights, complete logarithmic coefficient blocks, real-branch information, retained source models, transported remainders, several specialized scales, and separate residual, numerical, and interval-certificate facilities. These are useful distinctions even when a built-in can compute the same displayed finite expression. Its native delegation layer now preserves a separate native-result contract rather than pretending every native formal order is a proved analytic remainder.\src{core}{public usage declarations, result construction and accessors}\src{native}{native result admission and analytic-operation guard}

Three conclusions follow from the inspected revision. First, the package has a substantive implementation and an unusually detailed record of known limitations; blanket descriptions such as ``only a prototype'' or ``does not support Mathics'' would conceal important work. The repository explicitly states these as goals, alongside coverage of the vendored asymptotics corpus. \section{Capabilities and comparison with Wolfram Language}
\subsection{The package's mathematical object}

An ordinary power-log result is naturally read in a positive local variable $u\to0^+$:
\begin{equation}\label{eq:germ}
 f(u)=\sum_{\alpha<\beta}u^\alpha P_\alpha(\log u)
       +\OO\!\left(u^\beta(1+|\log u|)^k\right).
\end{equation}
The code stores a finite collection of exact weights and polynomial logarithmic coefficients, with a remainder frontier and its logarithmic degree. The local variable is a sided displacement at a finite endpoint, or an appropriate reciprocal coordinate at infinity. The public descriptor \code{PowerLogRemainder[u,beta,k]} is an inert mathematical remainder class, not a numerical interval.\src{core}{\code{PowerLogRemainder} usage, local-coordinate consumers and inverse result assembly}

Complete blocks are important. If two contributions have the same weight, their entire coefficient polynomial must be combined before determining the first omitted logarithmic degree. Conversely, $u^\alpha$ and $u^\gamma$ with distinct irrational weights need not fit a common rational lattice. These representation choices explain part of the package's utility without implying that every native asymptotic expression must fit a single \code{SeriesData} object.

For a normalized inverse problem
\begin{equation}\label{eq:inversemodel}
 y-y_0=a u^p\left(1+\sum_j u^{\delta_j}B_j(\log u)\right),
\end{equation}
the ordinary engine works with positive gaps, an explicit real branch, and a uniformizer based on $((y-y_0)/a)^{1/p}$. Direct Lagrange, grouped Lagrange, Newton and incremental scheduling are existing mechanisms. The result retains its model, assumptions, source and target coordinates, coefficient blocks, and optional native view. Their existence should not be repackaged as proposed future features.\src{core}{ordinary inverse construction, model and result fields}\src{status}{P03--P08 and already implemented mechanisms}

Other constructors deliberately leave this ordinary representation. Lambert/logarithmic inverses, Gamma and Barnes inverses, exact exponential-core corrections, finite Fourier-polynomial coefficients, and flat exponential sectors have their own small variables and truncation meanings. This is a collection of specialized, cooperating calculi; it is not yet evidence of a universal transseries algebra.\src{lambert}{\code{lambertConstruct}}\src{expcore}{\code{exponentialCoreConstruct}}\src{fourier}{Fourier coefficient and jet algebra}

These built-ins are natural controls for overlapping admitted problems. Neither overlap nor a different output representation makes the package redundant.\src{wl-inverseseries}{scope and ramified reversion examples}\src{wl-asymptoticsolve}{supported asymptotic equation-solving forms}

\subsection{Routing and observable behavior}

The inspected dispatcher admits \code{"Package"}, \code{"Series"}, \code{"Asymptotic"}, and \code{Automatic}. Native requests and native options can be delegated before real-coordinate admission. Automatic routing retains a successful package expansion and can search compatible native backends on admitted routes. Explicit package-only branch, direction or resource constraints are not meant to be silently discarded to make fallback succeed. Several request-resolution edge cases are already tracked by wave 3 and are not new findings in this article.\src{native}{\code{expansionDispatch}, \code{automaticProtectedQ} and native search}\src{wave3}{W3-01--W3-05 and W3-09}

The native representation is a useful design decision. A computed native output, a formal order term, and a package analytic remainder theorem are different kinds of evidence. The package keeps those distinctions in metadata and rejects operations that require a package analytic contract when only a native result is available. A native \code{Normal} can also retain an infinite expression; it is not universally a finite polynomial.\src{native}{\code{requireAnalyticSeries} and native result construction}\src{core}{\code{GeneralizedSeries} usage}

At the ordinary object boundary, \code{Normal[s]} returns the stored expression, while numerical application substitutes a value into that expression. This is convenient, but it makes the evaluator used by a retained special-function core part of the operational contract. F3 is a concrete consequence: a mathematically correct symbolic formula can remain unsafe to specialize through a defective interpreter implementation. That is more specific than the existing general proposal for a checked numerical evaluator.

\section{F1: the portable runner can forget a detected source change}
\subsection{Mechanism and consequences}

The portable runner's purpose is appropriate: launch fresh kernels, enforce process timeouts, require a matching result protocol, retain diagnostics and reject changed-source runs. It freezes the test-suite text before executing cases. However, \code{write_report} recomputes
\begin{lstlisting}
"SourcesUnchangedDuringRun": before == after
\end{lstlisting}
on each call and overwrites the report. The final return code consults the last report's value. Nothing accumulates the fact that an earlier comparison was false.\src{runner}{\code{fingerprints}, \code{write_report} and final return; lines 204--256}

Let $S_0$ be the initial tracked source state and $S_i$ the state after case $i$. The intended claim requires at least
\begin{equation}\label{eq:sticky}
 U_n=\bigwedge_{i=0}^{n}[S_i=S_0].
\end{equation}
The implemented final predicate is only $[S_n=S_0]$. Thus an $A\to B\to A$ history can pass. The stronger point is that this is not merely a change occurring invisibly between observations: in the supplied fixture the runner observes $B$, writes a false unchanged flag, and subsequently erases that evidence when the source returns to $A$.

This can turn a mixed-source run into a success record. It does not establish that any historical repository receipt was actually contaminated; no such accusation is supported. It does establish that the present mechanism cannot justify its unchanged-during-run assertion in the reproduced scenario.

\subsection{Executed reproduction}

\path{code/reproduce_runner.py} copies the exact pinned upstream runner into a temporary fixture. A small executable emits the runner's required protocol and is explicitly identified as \code{PROTOCOL-ONLY-FAKE-KERNEL}. One case changes a watched source; the next reads the intermediate report and restores the source. This tests the runner's control flow and evidence handling. It does not test the asymptotic package, Mathematica, Mathics, or mathematical correctness of a test expression.

\subsection{A narrow, tested repair}

The supplied patch adds a nonlocal sticky predicate:
\begin{lstlisting}[language=Python]
sources_unchanged = True

def write_report(complete: bool) -> dict:
    nonlocal sources_unchanged
    after = fingerprints(source)
    sources_unchanged = sources_unchanged and before == after
    # ...
    # "SourcesUnchangedDuringRun": sources_unchanged
\end{lstlisting}

This repair is small enough to review independently. The exact diff is in \path{code/runner_sticky_flag.patch}; the fixture applies and executes it. A production revision should additionally retain the first detected mismatch and the affected paths after restoration. The minimal patch preserves the invalidation decision, but the upstream report's conditional after-state field can still disappear once the files match again. A false final unchanged flag without the original mismatch details is preferable to a false success, yet it is not the most useful diagnostic.

Equation~\eqref{eq:sticky} still observes only snapshots. A mutation and restoration entirely between comparisons remains undetectable. The complete repair is therefore to freeze the selected source inputs as well as the suite, execute that frozen selection, and separately invalidate changes to the intended inputs or tooling. Source freezing and a sticky invalidation flag solve different problems and should not be treated as alternatives.

\section{F2: relocated modular dependencies can escape monitoring}
\subsection{The naming-dependent source set}

The same runner includes sibling Wolfram Language modules in its monitored set only when both the entry filename and parent-directory basename match a specific layout:
\begin{lstlisting}[language=Python]
if source.name == "AsymptoticAnalysis.wl" and source.parent.name == "Kernel":
    files.update(source.parent.glob("*.wl"))
\end{lstlisting}
The package loader, by contrast, derives its module directory from the entry file's location and uses relative \code{Get} calls. A copied modular package does not need the enclosing directory to be literally named \code{Kernel}. A path accepted for loading can therefore have a different monitored dependency set merely because its directory was renamed.\src{runner}{\code{fingerprints}, lines 45--56}\src{core}{\code{$kernelDirectory} and module-loading block}

The executed fixture places the entry and a sibling under \code{RelocatedModules}, permanently changes the sibling, and emits a successful protocol result. The runner's monitored set omits that sibling, its final unchanged flag is true, and its exit code is zero. The sibling remains changed at completion. This is independent of F1: no restoration or lost intermediate flag is needed.

The fixture's synthetic kernel does not actually execute the sibling as Wolfram Language. That is unnecessary to demonstrate the monitoring omission, but it bounds the claim. The fact that real package loading consumes relative siblings follows from the inspected loader, not from pretending the synthetic fixture executed the package.

\subsection{Select inputs explicitly, then stage them}

A robust source contract should distinguish modular and standalone loading explicitly. For the known modular layout, select the required module set independently of the destination directory's name; for a standalone source, select the single generated file. An explicit mode or an explicit source manifest is less ambiguous than guessing from a basename. Conservatively monitoring every sibling \code{.wl} file is an acceptable interim policy, with the documented cost that unrelated sibling edits can invalidate a run.

The bundle provides \path{code/stage_git_sources.py}. It takes a repository, an immutable full commit ID, an unused output path, and a modular or standalone mode. It reads the selected bytes from Git objects rather than from the live working tree. Modular mode stages the tracked \code{.wl} files beneath the known \path{src/Kernel} layout and preserves their relative module paths. It refuses an existing destination rather than silently merging two source versions.

A synthetic local Git experiment committed \code{value=1;} in a helper, changed the working-tree helper to \code{value=999;}, then staged the committed revision. The staged helper remained \code{value=1;}. This result is recorded in \path{evidence/staging_experiment.json}. It demonstrates the proposed utility's central property; it is not a run of the Asymptotic source tree.

This utility is intentionally not a general dependency resolver, a read-only filesystem sandbox, or an arbitrary-code security boundary. A future module that reads another data file requires that file to enter the selected input set. The frozen suite, capture tooling, and source selection must be treated together. The repository's separate definition-comparison tooling already takes source freezing seriously; the improvement here is to give the portable behavioral runner the same evidential discipline, not to claim that no frozen-input tooling exists.\src{compat}{native definition comparison and frozen capture-script workflow}

\section{F3: a retained exact core can outlive an unsafe evaluator}
\subsection{The existing principal-branch workaround is useful but incomplete}

The repository already documents a Mathics two-argument \code{ProductLog} problem and deliberately normalizes principal-branch construction sites to the one-argument form. It also explicitly states that numerical nonprincipal Lambert evaluation remains unsupported. This review does not rediscover that documented interpreter issue. The additional concern is how the remaining unsafe form interacts with a public result that exposes its exact core through ordinary numerical substitution.\src{compat}{Fourier and exact cores}\src{mcore}{\code{mathicsCoreProductLog} and rewritten construction sites}

The Mathics helper makes the distinction visible:
\begin{lstlisting}
mathicsCoreProductLog[0, argument_] := System`ProductLog[argument];
mathicsCoreProductLog[branch_, argument_] :=
    System`ProductLog[branch, argument];
\end{lstlisting}
The principal branch is normalized, but a nonprincipal branch is forwarded to the two-argument implementation. Leaving a symbolic unsupported expression available for inspection can be legitimate. Silently applying an evaluator known to give a different function is a different matter. The generic \code{GeneralizedSeries} numerical accessor substitutes into the stored expression; there is no branch-specific capability refusal at that boundary in the inspected code.\src{core}{\code{GeneralizedSeries[a][val_?NumericQ]}}

\subsection{A sharper diagnosis: the exact SymPy conversion path}

The Mathics 10.0.1 \code{ProductLog} class declares \code{sympy_name = "LambertW"}. Its inherited \code{prepare_sympy} leaves the argument sequence unchanged, and the generic converter applies the corresponding SymPy function to those arguments. Wolfram's two-argument order is branch first; SymPy's is argument first. Thus a generic unpermuted conversion maps
\begin{equation}\label{eq:wrongconversion}
 \code{ProductLog[k,z]}\quad\longmapsto\quad
 \code{sympy.LambertW(k,z)},
\end{equation}
rather than \code{sympy.LambertW(z,k)}.\src{mathics-productlog}{\code{ProductLog} class}\src{mathics-builtin}{\code{SympyFunction.prepare_sympy}, \code{to_sympy}, and exact-input branch of \code{MPMathFunction.eval}}

This diagnosis is narrower and more precise than saying that every bad call is caused directly by mpmath argument order. The inspected superclass has a separate numerical arity mechanism; no direct two-argument mpmath call needs to be assumed to establish the exact-conversion mismatch. The supplied independent SymPy 1.14.0 experiment evaluates both orders:
\begin{align*}
 \operatorname{LambertW}(-1/10,-1)
  &\simeq -3.577152063957297218409391963512,\\
 \operatorname{LambertW}(-1,-1/10)
  &\simeq -0.318131505204764135312654251588\\
  &\qquad{}+1.337235701430689408901162143194\,i.
\end{align*}
The principal control is equally diagnostic: the unpermuted \code{LambertW(0,E)} is $-\infty$ in that experiment, whereas \code{LambertW(E,0)} is $1$. These are independent backend observations recorded in \path{evidence/mathematical_oracles.json}, not a fresh Mathics session.

\subsection{The concrete package path to characterize}

Consider
\begin{equation}\label{eq:expcore}
 F(x)=\frac{e^x}{x},\qquad x>1.
\end{equation}
The selected increasing inverse is
\begin{equation}\label{eq:lowerinverse}
 x(y)=-W_{-1}(-1/y),\qquad y>e.
\end{equation}
The branch follows immediately from $(-x)e^{-x}=-1/y$ and $x>1$. The usual real Lambert branches are described by DLMF \S4.13; the domain and identity needed here also follow directly from this equation and the derivative below.\src{dlmf-lambert}{defining equation and real branches}

The package's exponential-core constructor recognizes $a v^b e^{c v^p}$ and chooses branch $-1$ for the growing branch when $b<0$. For \eqref{eq:expcore}, its parameters are $a=c=p=1$ and $b=-1$, so its exact core is precisely \eqref{eq:lowerinverse}. When the perturbation is zero, the inspected constructor's algebra makes the expression the exact source inverse and its sector remainder zero.\src{expcore}{\code{exponentialCoreExactInverse} and the zero-perturbation branch of \code{exponentialCoreConstruct}}

The supplied public characterization is:
\begin{lstlisting}
s = AsymptoticExponentialCoreInverse[
    Exp[x]/x, 0, {x, Infinity}, {y, 0}];
Normal[s]
N[s[10], 30]
\end{lstlisting}
The correct inverse at $y=10$ is approximately $3.577152063957297218409391963512$. If the unsafe unpermuted conversion is reached, the inverse would instead be the negative of the second value above: approximately $0.3181315052-1.3372357014i$. A complete Mathics run may fail at an earlier admission or simplification step, and this review has not established otherwise. Therefore this is a \emph{source-traced public candidate}, not a claimed observed complex package answer.

An important acceptance distinction follows. A clear unsupported-evaluator failure can be correct behavior until the numerical branch is implemented. An object that honestly retains a symbolic core can also be useful. An apparently successful numerical value for a different branch or function is not an acceptable substitute. A zero asymptotic remainder certifies the mathematical representation of an exact core; it does not certify the interpreter implementation used to evaluate that core.

\subsection{Safe containment and a bounded constructive alternative}

The immediate containment proposal is to attach numerical capability to the retained core and refuse unsupported two-argument evaluation before substitution. \path{code/CandidateAdapters.wl} contains a separate-context guard illustrating that boundary. It is unexecuted, not installed into the package, and not a general domain or error checker. It only screens an exposed two-argument \code{ProductLog}; it cannot repair an expression already corrupted by earlier evaluation. A production fix must guard construction and specialization sites that can evaluate the head before such a late screen runs.

For the real lower branch there is also a small alternative that does not require a general complex Lambert implementation. The accompanying Python code computes a rational enclosure for \eqref{eq:expcore} on $x>1$ using only exact exponential bounds and monotonicity. It never calls Lambert $W$ to make a proof decision.

\begin{lemma}[Rational enclosure of an exponential]\label{lem:exp}
For rational $x\ge0$, let $S_n=\sum_{j=0}^n x^j/j!$ and suppose $q=x/(n+2)<1$. Then
\begin{equation}\label{eq:expbound}
 S_n\le e^x\le S_n+
       \frac{x^{n+1}}{(n+1)!}\frac{1}{1-q}.
\end{equation}
\end{lemma}
\begin{proof}
All omitted terms are nonnegative. Starting after the first omitted term, each successive ratio is $x/(j+1)\le x/(n+2)=q$. A geometric series therefore majorizes the omitted tail. Every endpoint in \eqref{eq:expbound} is rational.
\end{proof}

\begin{proposition}[A certified increasing inverse enclosure]\label{prop:inverse}
Let $y>e$ be rational. Suppose rational $1\le l<r$ satisfy a proved upper bound $U_l<yl$ for $e^l$ and a proved lower bound $L_r>yr$ for $e^r$. Then the unique solution of \eqref{eq:expcore} lies in $(l,r)$.
\end{proposition}
\begin{proof}
The endpoint inequalities give $F(l)<y<F(r)$. Continuity gives a root. Moreover
\[
 F'(x)=\frac{e^x(x-1)}{x^2}>0\quad (x>1),
\]
so there is at most one root on the increasing branch. The endpoint at $l=1$ causes no ambiguity because $F(1)=e<y$ and strict increase holds to its right.
\end{proof}

The implemented procedure verifies the left endpoint, doubles a right endpoint until its sign is proved, and bisects with rational arithmetic. When a residual sign cannot yet be decided, it tightens the exponential enclosure instead of guessing. Resource exhaustion is an explicit exception. The implementation has finite arithmetic and bracketing budgets; it is not claimed to certify every rational input within those budgets.

For $y=10$, the executed code obtains
\begin{equation}\label{eq:exactinterval}
 \frac{16892623010959913834611}{4722366482869645213696}
 <x(10)<
 \frac{67570492043839655338447}{18889465931478580854784}.
\end{equation}
The width is $3/18889465931478580854784<2^{-72}$. The runs at $y=3,10,100$ all met the same requested width. mpmath values were used only as an independent numerical cross-check after the exact decisions. This is a certificate for the original core equation, not merely for a finite asymptotic model; it is not yet integrated with the Wolfram Language package.

\section{F4: resource semantics can change inside compatibility adapters}
\subsection{Sparse coefficient rules become a dense list}

The Mathics algebra adapter supplies a univariate \code{CoefficientRules} by expanding a polynomial, forming \code{CoefficientList}, assigning exponent indices and removing zeros.\src{malgebra}{univariate \code{CoefficientRules} definition}
The last filter restores a sparse \emph{output}, but it does not undo the dense allocation already performed.

For the family
\begin{equation}\label{eq:sparsefamily}
 P_D(z)=a+bz^D,\qquad D\in\NN,
\end{equation}
with nonzero coefficients independent of $z$, the natural sparse support has size two. A coefficient list has $D+1$ positions. Thus this implementation performs at least degree-proportional list construction even though the input can encode $D$ in $\OO(\log D)$ bits and the output remains two rules. At $D=10^6$ the dense list has $1{,}000{,}001$ positions; at $D=10^{12}$ it would have $1{,}000{,}000{,}000{,}001$. These are structural counts, not measurements of allocated memory, byte size, or a completed benchmark.

No huge polynomial was allocated to demonstrate this cost. \path{evidence/mathematical_oracles.json} explicitly records zero allocated test slots for these structural examples. A deliberate out-of-memory experiment would add little evidence to the source-level allocation argument and could obscure the distinction between a predictable complexity problem and a runtime measurement.

This path is different from the previously reviewed optional \code{SeriesData} export and from eager normalization of a native result. Those mechanisms have their own guards or open work. Here the intermediate coefficient provider itself becomes dense. The broad P06 resource taxonomy already exists; the new contribution is a concrete additional adapter where the taxonomy must be enforced.

\subsection{A local sparse alternative, with honest limits}

For an already expanded univariate polynomial, collect each monomial's exponent and coefficient, merge equal exponents and sort the surviving rules. The prototype \code{SparseCoefficientRules1} in \path{code/CandidateAdapters.wl} implements this idea without \code{CoefficientList}. Its intended behavior is
\begin{lstlisting}
SparseCoefficientRules1[a + b z^D, z]
(* {{D} -> b, {0} -> a}, for positive integer D *)
\end{lstlisting}
It is an unexecuted Wolfram Language candidate, not a demonstrated Mathics repair. Its precondition excludes nonpolynomial or variable-dependent ``coefficients.'' Zero handling and deterministic exponent ordering are explicit; algebraic zero detection still depends on the admitted coefficient conventions.

The replacement does not make the entire package sparse. Existing core and Fourier paths also use dense coefficient lists for logarithmic polynomials, and \code{Expand} can itself produce excessive work before a sparse collector runs. Those are separate costs. The useful invariant is narrower: \emph{a sparse-to-rule adapter should not allocate all absent degrees solely to recover two occupied ones}. Admission, expression expansion, coefficient normalization, and final support budgeting should each retain their own resource meaning.

For a production acceptance test, instrument the adapter's dependency on \code{CoefficientList} or its allocation path, keep support fixed while increasing $D$, and separately measure expansion time, collection time and peak memory. Compare both output coefficients and refusal behavior. An implementation that silently drops high-degree terms to meet a budget is not an optimization of this contract.

\subsection{First-position lookup has a related materialization cost}

The Mathics compatibility helper for \code{FirstPosition} correctly addresses pattern matching, a lazy default and \code{Heads}; however, it first computes all matching positions and then takes the first.\src{mcompat}{\code{firstPosition} helper}
On an expression with $m$ matching nodes, this creates a list of all $m$ positions for a result that needs one. This is a resource observation, not a claim that the result is mathematically wrong for ordinary pure patterns. Wolfram's documentation itself explains first-position behavior through position-based constructions, so a stylistic objection to using \code{Position} would miss the actual issue.\src{wl-firstposition}{search behavior, levels and heads}

A bounded search is worth evaluating, either through a supported maximum-match form or an explicit traversal preserving the same level, head and ordering semantics. It must be checked on the actual Mathics version; assuming every native \code{Position} form is implemented would repeat the compatibility error the adapter was created to avoid. The supplied predicate-count probe is only a characterization. No timing advantage, exact predicate count, or full parity of a replacement is claimed here.

\section{F5: a private limit default is not the native default}

The Mathics limit wrapper translates explicit direction strings correctly according to the intended real-side convention: \code{"FromAbove"} becomes $-1$ and \code{"FromBelow"} becomes $1$. But it also maps its default \code{Automatic} to $1$, the limit from below.\src{msimplify}{\code{Options[Limit]} and the direction replacement}

Current Wolfram documentation specifies \code{Direction -> Reals} as the default for \code{Limit}: the real two-sided limit. This must not be confused with either one-sided convention.\src{wl-limit}{options and two-sided real limit examples}\src{wl-direction}{direction aliases}
The elementary witness is
\[
 h(x)=\frac{|x|}{x},\qquad
 \lim_{x\to0^-}h(x)=-1,\qquad
 \lim_{x\to0^+}h(x)=1.
\]
There is no two-sided real limit. An omitted-direction helper that delegates to the left side asks a different question. The independent Python oracle confirms the two one-sided values; a live Mathics call to the package helper is supplied but unexecuted.

This is presently a private-helper contract hazard, not an established public wrong result. An inspected consumer in the native special-function adapter explicitly asks for \code{"FromAbove"}, and therefore avoids the default. Other consumers need an occurrence-level audit or runtime instrumentation before attributing a public failure to this helper.\src{native-special}{\code{specialNativeSmallQ}}

The repair must not simply change $1$ to $-1$. That would exchange one incorrect default for another relative to Wolfram's two-sided semantics. There are two sound designs. A narrowly named positive-local-coordinate limit helper can require an explicit side and reject omission. Alternatively, a compatibility wrapper can implement a finite-real two-sided query by obtaining both one-sided results, proving equality where possible, and retaining a distinct unresolved state when the comparison cannot be established. Unequal proved finite limits justify nonexistence; two unresolved expressions do not.

Infinite endpoints and complex directions require their own semantics and must not be handled by blindly duplicating the finite real recipe. The practical first step is to make every current internal use state its intended side. That both documents the asymptotic chart and removes accidental reliance on a default whose meaning changes between runtimes.

\section{F6: a bounded hypergeometric extension with error bounds}
\subsection{The present admission rule is conservative}

The Mathics defining-Taylor adapter accepts a constant multiple of one recognized special-function atom at a vanishing monomial argument. It verifies exact arity, independence of parameters from the local variable, a positive integral monomial degree, and an explicit finite order. For hypergeometric functions it also requires real upper parameters, positive lower parameters, and $p\le q+1$. A rejected defining-series request falls back to the interpreter's native \code{Series} path.\src{mtaylor}{defining-series admission and Taylor dispatch}

These restrictions are defensible as a first implementation. They are not all necessary mathematical restrictions. In particular, a negative nonintegral lower parameter need not cause a denominator pole, and a terminating hypergeometric polynomial does not need the nonterminating convergence-rank restriction. This section proposes a bounded extension, not a claim that a public request necessarily fails today: native simplification or fallback may already resolve individual examples.

The ordinary defining coefficients are
\begin{equation}\label{eq:hgcoeff}
 c_n=\frac{(a_1)_n\cdots(a_p)_n}{(b_1)_n\cdots(b_q)_n\,n!},
 \qquad H(z)=\sum_{n\ge0}c_nz^n.
\end{equation}
Excluding nonpositive integral lower parameters avoids denominator zeros. For a nonterminating defining Taylor series, $p\le q$ gives an entire function, while $p=q+1$ has unit convergence radius. A nonpositive integral upper parameter terminates the series even when $p>q+1$. These standard defining-series facts supply the starting point, not the quantitative bound developed below.\src{dlmf-hg}{\S16.2(i)--(iv)}

A safe first extension can be restricted to exact rational parameters. It need not solve general symbolic integer-membership questions. It should reject every lower parameter in $\{0,-1,-2,\ldots\}$ until a regularization or limiting convention is explicitly selected. Allowing upper and lower negative integers to ``cancel'' without specifying that convention would change the mathematical object. The accompanying prototype deliberately refuses these ambiguous cases, including a matching upper/lower value of $-2$.

\subsection{Coefficient recurrence and exact termination}

Starting at $c_0=1$, use
\begin{equation}\label{eq:hgrecurrence}
 c_{n+1}=c_n\,
   \frac{\prod_{i=1}^p(a_i+n)}{(n+1)\prod_{j=1}^q(b_j+n)}.
\end{equation}
Under the denominator admission rule this uses only rational arithmetic for rational parameters. If the earliest terminating upper parameter is $-m$, all coefficients above $m$ are zero. Termination should be recognized before applying a convergence test appropriate only to a nonterminating series. It should also be recorded as an exact polynomial result once all coefficients through degree $m$ are retained.

Two independently executed examples are
\begin{align}
 {}_0F_1\!\left(; -\tfrac12;z\right)
   &=1-2z-2z^2-\tfrac49z^3-\tfrac{2}{45}z^4+\OO(z^5),\label{eq:0f1}\\
 {}_3F_0(-2,1,1;;z)&=1-2z+4z^2.\label{eq:3f0}
\end{align}
The first uses a negative nonintegral denominator parameter; the second terminates despite exceeding the current rank gate. The coefficients follow directly from \eqref{eq:hgrecurrence}. They are suitable independent regression oracles, unlike copying the candidate implementation's own result into its expected-output field.

\subsection{A finite-radius tail theorem}

To import a Taylor model into an analytic remainder calculus, a coefficient list alone is not the strongest available evidence. The following elementary majorant provides an explicit bound for this restricted family.

\begin{proposition}[A uniform hypergeometric Taylor-tail bound]\label{prop:hgtail}
Assume the series in \eqref{eq:hgcoeff} is nonterminating, its lower parameters avoid nonpositive integers, and $p\le q+1$. Let $r\ge0$ and choose an integer $J\ge1$ such that $J>\max_j|b_j|$ (taking that maximum as zero for an empty lower-parameter list) and
\begin{equation}\label{eq:QJ}
 Q_J=r J^{p-q-1}
       \frac{\prod_i(1+|a_i|/J)}{\prod_j(1-|b_j|/J)}<1.
\end{equation}
For truncation after degree $m$, put $L=\max\{m+1,J+1\}$. Then, uniformly for $|z|\le r$,
\begin{equation}\label{eq:hgtail}
 \left|H(z)-\sum_{n=0}^m c_nz^n\right|
 \le \sum_{n=m+1}^{L-1}|c_n|r^n+
      \frac{|c_L|r^L}{1-Q_J}.
\end{equation}
For $p\le q$, a sufficiently large $J$ exists for every finite $r$; for $p=q+1$, one exists whenever $r<1$.
\end{proposition}
\begin{proof}
The case $r=0$ is immediate. Assume $r>0$. For $n\ge J$, the ratio of successive absolute term majorants satisfies
\begin{align*}
 \frac{|c_{n+1}|r^{n+1}}{|c_n|r^n}
 &=r\frac{\prod_i|n+a_i|}{(n+1)\prod_j|n+b_j|}\\
 &\le r n^{p-q-1}
      \frac{\prod_i(1+|a_i|/n)}{\prod_j(1-|b_j|/n)}
 \le Q_J.
\end{align*}
The first inequality uses $n+1\ge n$ and $|n+b_j|\ge n-|b_j|>0$. The second uses $p-q-1\le0$ and monotonic bounds on each factor for $n\ge J$. Summing the tail from $L$ geometrically gives \eqref{eq:hgtail}; the earlier omitted terms are a finite explicit sum. Finally $Q_J\to0$ for $p\le q$ and $Q_J\to r$ for $p=q+1$, proving the existence statements. In a terminating case the tail is instead a finite exact sum, so no ratio theorem is needed.
\end{proof}

The Python prototype searches a bounded sequence of $J$ values, refuses when it cannot establish $Q_J<1$ within its budget, and reports the selected ratio bound. Thus the mathematical existence statement is stronger than the finite implementation's coverage, as it should be.

\subsection{Transport to the package's monomial input}

The present adapter admits an argument $z=c t^d$, with fixed $c$ and positive integral $d$, and an outer constant multiplier $A$. Choose a radius $\rho$ with $|c|\rho^d\le r$. Substituting into a proved defining-series tail gives
\[
 |A|\left|H(c t^d)-\sum_{n=0}^m c_n c^n t^{dn}\right|
 \le |A|B_r,\qquad |t|\le\rho,
\]
where $B_r$ is the right-hand side of \eqref{eq:hgtail}. To express a vanishing-order bound rather than just a uniform absolute number, apply the same ratio majorant after factoring $|c t^d|^{m+1}$ from the omitted tail. This yields a computable constant times $|t|^{d(m+1)}$ on the chosen neighborhood.

An implementation must retain the distinction between polynomial degree in $z$ and the requested order in $t$. The least omitted power comes from $d(m+1)$, not automatically from $m+1$. An outer pole is not a constant multiplier and must not be admitted by this adapter without a separate order-transport argument. The current code's constant-multiplier restriction is therefore worth preserving.

This extension can be implemented first as an internal defining-series provider, with a small explicit admission predicate and independent tests from the supplied recurrence and bounds. It should not silently broaden to divergent nonterminating ${}_pF_q$ expansions, analytic continuation across branch cuts, regularized functions, or arbitrary symbolic parameter domains. Those are different contracts.

\section{Conclusion}

The inspected revision has clear mathematical strengths: specialized exact-weight calculi, explicit real branches, retained precision information, exact cores and a native-result contract that avoids conflating formal output with analytic evidence. Its Mathics work is substantial and deliberately conservative, but complete compatibility remains unproved and explicitly unfinished in the repository's own records.

The strongest new findings are not speculative algebraic counterexamples. They are two reproduced defects in the current portable runner's connection between observations and source identity. Repairing that connection is a prerequisite for trustworthy compatibility claims. The other new results are deliberately narrower: a lower-Lambert specialization risk traced to an exact conversion path, a degree-sized allocation inside a sparse-looking Mathics adapter, and a private limit default that asks a different question from the current native default.

The accompanying code moves beyond criticism without overstating completion. One provenance repair is tested against the actual runner. Immutable source staging is demonstrated independently. The original exponential-core equation receives exact rational enclosures, and a bounded hypergeometric extension receives explicit coefficients and a proved tail majorant. The remaining Wolfram and Mathics experiments are supplied as concrete, unexecuted acceptance work. These results add to the existing review program without relabeling its backlog as new discoveries.

\section{Minimal regression specifications}

\textbf{F1 invariant.} Once a source comparison is false, every later report from that invocation must remain invalid, even if all watched files are restored byte-for-byte. Preserve the first mismatch details. An unchanged run must remain admissible.

\textbf{F2 invariant.} Renaming a correctly relocated modular directory must not remove a loaded sibling from the selected source set. A standalone entry must remain distinguishable from modular loading without depending solely on the destination basename.

\textbf{F3 invariant.} A mathematically admitted lower-real Lambert core must either specialize through a tested branch-correct evaluator or return an explicit unavailable-capability result. A high-precision number for the wrong function cannot count as compatibility. Both principal and lower-branch controls are required.

\textbf{F4 invariant.} For an admitted expanded polynomial with fixed support, coefficient-rule collection must not allocate every absent degree merely to filter them out. Preserve zero, coefficient and ordering semantics. Bound expansion separately.

\textbf{F5 invariant.} A finite real two-sided query cannot be satisfied by one side alone. Explicit local-side requests must be preserved. Unknown one-sided information or unproved equality remains unresolved rather than guessed.

\textbf{F6 invariant.} Lower denominator poles are refused unless a different mathematical convention is explicitly selected. A terminating series can bypass the nonterminating rank condition, but exactness is asserted only when the retained finite polynomial is complete. Every nonterminating analytic import retains a justified tail.
