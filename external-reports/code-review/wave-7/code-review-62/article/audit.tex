\begin{abstract}
This is an incremental review rather than another copy of the repository's extensive existing backlog. Inspection covered central construction, arithmetic, inverse, special-function, numerical-evidence and compatibility paths, with focused execution on the pinned standalone package. One new root cause is admitted to the findings register: live branch and assumption predicates are duplicated during ordinary binary arithmetic. The alignment stage already combines both operands' conditions, but the final result construction combines the left operand again. With a fixed independently constructed zero series, the number of copies of a single domain predicate is $2^{n+1}-1$ after $n$ additions. With the ordinary scalar zero, operand promotion inherits the current conditions and the observed recurrence becomes $3^n$.

The distinction from previously reported recipe/provenance growth matters: this defect is visible in the current \code{TargetDomain} alone, before serialization or refinement. The most obvious one-line repair is incomplete; a native test shows that scalar growth merely changes from $3^n$ to $2^n$. A stronger candidate combines duplicate-free structural conjunction with single ownership of the aligned condition set. Selected native tests retain one predicate throughout and preserve branch restrictions. The accompanying independent tests establish the count model, Boolean equivalence and guarded source transformation, not interpreter correctness. The article details the source path, mathematical invariant, repair boundary, portability obligations and precise remaining acceptance work.
\end{abstract}

\section{The representation boundary that fails}
\label{sec:path}

\subsection{A series object carries more than its printed expression}
A derived ordinary result stores a finite expression, a remainder, an internal series representation, assumptions, a target domain and a refinement recipe. In \code{seriesMake}, the current representation's \code{Domain} is copied into the public \code{TargetDomain}; the representation itself is retained separately. The same function performs real-coefficient validation using the current proof environment. These facts make the size of operational conditions relevant even when the expression and coefficient support are tiny.\cite[lines 100--121]{operations}

For the witness, the mathematical data are deliberately uninteresting:
\[
 F(x)=x,\qquad Z(x)=0,\qquad x\to0^+.
\]
Both are exact. Adding $Z$ neither increases the number of nonzero coefficient blocks nor creates an unknown tail. The initial target condition is simply $D=(x>0)$. Counting copies of $D$ in \code{TargetDomain} therefore isolates a bookkeeping failure rather than a difficult asymptotic calculation.

The arithmetic path is:
\begin{lstlisting}
SeriesAdd[s, t]
  -> seriesArithmeticPublicBinary["Add", ...]
  -> seriesArithmeticBinary["Add", ...]
  -> seriesRegularOperand[t, s, ...]  (* only for regular t *)
  -> seriesBinary["Add", s, operand, ...]
  -> seriesMake[representation, recipe, ...]
\end{lstlisting}
The public layer validates the cutoff and controls automatic arithmetic; the inner dispatcher admits analytic objects, handles other scale families, promotes ordinary operands, and enters the ordinary binary engine. Those layers explain why an explicit call with scalar \code{0} is not the same construction path as a call with an independently created zero series.\cite[lines 35--92]{arithmetic}

\subsection{Alignment already intersects both condition sets}
After validating compatible variables, scales and branch domains, \code{seriesBinary} aligns the right representation with the left logarithmic variable:
\begin{lstlisting}
a = seriesData[s, limit];
b = seriesData[t, limit];
seriesCompatible[a, b];
b = seriesAlign[a, b];
\end{lstlisting}
The alignment definition is:
\begin{lstlisting}
seriesAlign[a_, b_] := Join[
  b /. b["LogVariable"] -> a["LogVariable"],
  <|"Assumptions" -> a["Assumptions"] && b["Assumptions"],
    "Domain" -> Lookup[a, "Domain", True] &&
                Lookup[b, "Domain", True]|>];
\end{lstlisting}
Thus, if the incoming condition expressions are $A$ and $B$, the local variable \code{b} now owns $A\land B$. It no longer contains only the original right operand's conditions. That ownership change is the key fact a reader must track.\cite[lines 123--135]{operations}

The subsequent optional flattening does not undo this change. \code{seriesFlat} either returns the existing representation or replaces only its prefactor, offset and jet. Its domain and assumptions remain attached. Consequently the final join still sees the aligned condition set in \code{b}.\cite[lines 93--99]{operations}

\subsection{The final merge adds the left conditions again}
Near the end of \code{seriesBinary}, the result is assembled with:
\begin{lstlisting}
d = Join[d, <|
  "Assumptions" -> a["Assumptions"] && b["Assumptions"],
  "Domain" -> Lookup[a, "Domain", True] &&
              Lookup[b, "Domain", True],
  "RemainderDerivativeOrder" -> order|>];
\end{lstlisting}
Because \code{b} is already aligned, this persists
\[
 A\land(A\land B)
\]
rather than one representation of $A\land B$. This is logically correct: conjunction is idempotent. It is not structurally economical. The native evaluator retains repeated symbolic predicates instead of automatically performing the needed idempotence reduction. A simple native control returned \code{a > 0 && a > 0} unchanged.\cite[lines 146--150]{operations}

There is also a temporary proof environment built from \code{seriesAss[a]} and \code{seriesAss[b]}. The supplied candidate deliberately leaves that expression unchanged: the persistent condition defect can be addressed without simultaneously redesigning all proof-call construction. This separation limits the repair's scope and makes its correctness argument inspectable.

\begin{proposition}[Fixed-right-operand growth]
Suppose the incoming left domain contains $d_n$ copies of one atomic predicate and the fixed right domain contains one copy. If the two joins above retain those occurrences, then
\[
 d_{n+1}=2d_n+1,\qquad d_0=1,
 \qquad\text{hence}\qquad d_n=2^{n+1}-1.
\]
\end{proposition}
\begin{proof}
Alignment contributes the $d_n$ left occurrences and one right occurrence to \code{b}. The final merge adds the $d_n$ left occurrences a second time. Solving the affine recurrence, or inducting directly, gives the formula.
\end{proof}
For the measured nontrivial conjunctions, the domain leaf count is $1+3d_n$: one conjunction head plus $d_n$ copies of a three-leaf comparison. The initial non-conjunction state has leaf count three. Both structural predictions match the table exactly.

\subsection{Scalar zero is worse}
\status{Executed on the unchanged pinned package in Wolfram 15.0.0}

Replacing the independently constructed \code{z} by scalar \code{0} produced:
\begin{lstlisting}
(* Repeated SeriesAdd[s, 0] *)
{{x, 3}, {x, 9}, {x, 27}, {x, 81}}
\end{lstlisting}
This is not contradictory evidence. \code{seriesRegularOperand} starts with \code{d = seriesData[s, limit]}, replaces the coefficient/offset/prefactor fields for the regular operand, and calls \code{seriesMake} while retaining \code{d}'s domain and assumptions. The promoted scalar therefore inherits all $d_n$ occurrences from the current left operand.\cite[lines 49--69]{arithmetic}

\begin{proposition}[Inherited-scalar growth]
For a promoted scalar operand whose condition expression is inherited from the left representation, the same implementation gives
\[
 d_{n+1}=3d_n,\qquad d_0=1,
 \qquad\text{hence}\qquad d_n=3^n.
\]
\end{proposition}
\begin{proof}
The promoted right operand contains $d_n$ occurrences. Alignment constructs $2d_n$ occurrences in \code{b}; the final result adds the original $d_n$ once again.
\end{proof}
The same source path is used for ordinary scalar multiplication. The complete candidate was tested on repeated multiplication by one; the unchanged baseline scalar-multiplication count is a source-derived prediction in the supplied runner, not an additional measured baseline result.

\subsection{Operation-order sensitivity}
For a fixed independently constructed left zero operand and a growing right operand, the source model predicts $d_{n+1}=d_n+2$, hence $d_n=2n+1$. In contrast, the measured fixed-right chain has $2^{n+1}-1$ occurrences. Consequently two mathematically equivalent ways to accumulate additions can have radically different condition-tree sizes. This particular commuted native chain was not measured; its count is an independently tested structural consequence of the source rule.

This is a useful acceptance dimension: verify equality of mathematical results and equivalence of domains, but also check that operand order does not introduce avoidable multiplicity growth. It does not follow that the entire result associations should be \code{SameQ}; recipes, stable predicate order and chosen representation may legitimately differ.

\subsection{Consequences without overstating them}
The observed defect can burden later real-coefficient checks, domain compatibility checks, printing, traversal and result manipulation. Those operations receive the enlarged conditions through the representation. A high-level caller can see a one-term exact answer while carrying hundreds of repetitions of the same restriction.\cite{operations}

The observations do not demonstrate that a wrong branch was accepted, that a coefficient became false, or that every arithmetic chain reaches a timeout. They do show unnecessary exponential structural work in an ordinary public path. Increasing \code{MaxTerms} or using a faster proof engine would not remove that construction error. Likewise, suppressing domain checking would be an unacceptable workaround: the restrictions remain necessary even when their repetitions are not.

\section{A repair that is sufficient for the demonstrated mechanism}
\label{sec:repair}

\subsection{The first repair is instructive but incomplete}
Since \code{b} already owns the combined conditions, the first candidate changed only the final persistent merge:
\begin{lstlisting}
d = Join[d, <|
  "Assumptions" -> b["Assumptions"],
  "Domain" -> Lookup[b, "Domain", True],
  "RemainderDerivativeOrder" -> order|>];
\end{lstlisting}
This is a genuine improvement for independently constructed fixed operands: its source recurrence is $d_{n+1}=d_n+1$. It is not a complete remedy for the normal scalar path. In a successful native source-substitution test, repeated \code{SeriesAdd[s,0]} returned:
\begin{lstlisting}
{{x, 2}, {x, 4}, {x, 8}, {x, 16}}
\end{lstlisting}
The repair changed the base of the exponential, not the nature of the scalar growth. The promoted scalar still brings a second copy of the current condition set into alignment.

The bundle retains \path{code/patch_merge_only.py} as an explicitly incomplete mechanism and regression counterexample. It should not be mistaken for the recommended fix. Recording this failed sufficiency test is important: a patch validated only with one fixed independent operand would appear successful while leaving the everyday scalar path defective.

\subsection{Give condition intersection an idempotent representation}
The stronger candidate makes two changes. First, alignment forms a duplicate-free conjunction of the already evaluated predicate expressions. Second, the final result keeps that aligned conjunction once.
\begin{lstlisting}
seriesConditionClauses[c_And] :=
  Flatten[seriesConditionClauses /@ (List @@ c), 1];
seriesConditionClauses[True] := {};
seriesConditionClauses[c_] := {c};

seriesConditionJoin[a_, b_] := And @@ DeleteDuplicates[
  Join[seriesConditionClauses[a], seriesConditionClauses[b]]];

seriesAlign[a_, b_] := Join[
  b /. b["LogVariable"] -> a["LogVariable"],
  <|"Assumptions" -> seriesConditionJoin[
      a["Assumptions"], b["Assumptions"]],
    "Domain" -> seriesConditionJoin[
      Lookup[a, "Domain", True], Lookup[b, "Domain", True]]|>];
\end{lstlisting}
This helper deliberately does \emph{less} than Boolean simplification. It descends only through top-level conjunctions, drops \code{True}, and removes structurally identical clauses. A disjunction is one opaque clause; it is not distributed. Distinct inequalities, parameter restrictions, quantifiers or other predicates are retained. The helper does not rewrite inside a held predicate or assert that two merely similar formulas are equivalent.

The stable first-occurrence order is useful for predictable output. It means the join need not be structurally commutative even though its truth condition is commutative. For example, the output order for $A\land B$ can differ from the output order for $B\land A$ without changing the admissible domain.

\begin{proposition}[Semantic preservation]
For already evaluated Boolean predicates $A$ and $B$, structural conjunction flattening, deletion of \code{True}, and removal of repeated identical clauses preserves $A\land B$. Replacing the old persisted $A\land(A\land B)$ by that normalized conjunction preserves the same truth condition.
\end{proposition}
\begin{proof}
Flattening uses associativity of conjunction. Removing \code{True} uses its identity law. Removing an identical clause uses idempotence. No operation distributes through disjunction, changes a predicate's variables, weakens an inequality, or depends on a solver establishing an additional theorem. Applying these laws to the old persisted conjunction gives the new one. A retained \code{False} still makes the result false.
\end{proof}

\begin{corollary}[Bounded multiplicity under repeated neutral operations]
For the demonstrated paths with a fixed finite set of distinct conjunctive clauses, duplicate-free alignment followed by single ownership of its result retains at most one occurrence of each such clause. This applies both to an independent fixed operand and to a scalar representation that inherits the current condition set.
\end{corollary}

This is a bound on repeated top-level clause occurrences, not a universal bound on predicate size. A single large disjunction remains large. Nor is a linear-time implementation of \code{DeleteDuplicates} assumed: exact structural comparison can have its own cost. The repair removes the exponential replication mechanism; it does not promise constant execution time for arbitrary condition formulas.

\subsection{What remains unchanged}
The candidate preserves \code{seriesCompatible}, the temporary proof environment, carrier alignment, jet addition and multiplication, real-coefficient validation, cutoff handling, derivative-order propagation, and refinement recipes. It does not strip conditions from a scalar merely because that scalar is zero or one. Instead it preserves the same conditions once. This avoids a second class of mistakes in which a neutral algebraic operation silently broadens the stated branch domain.

The choice to normalize in \code{seriesAlign} matters. Merely deduplicating the final printed domain would leave the internal representation and intermediate use of \code{b} inconsistent. Conversely, deleting the condition merge from alignment without checking its consumers would remove joint assumptions available while flattening the right representation. The two-site candidate retains those joint assumptions and gives their persistence a clear owner.

\section{Distinction from the existing review backlog}
\label{sec:novelty}
The nearest existing finding is P07, which concerns nested recipes, whole retained operands, cached state and provenance serialization. Report 1 A13 requests storage profiling; report 4 A04 gives an abstract repeated-self-multiplication recipe-tree recurrence and recommends a shared graph. Those observations are not reissued as new recommendations here.\cite{status,prior1,prior4}

CG-01 differs in four concrete respects. Its measured quantity is the \emph{current operational domain}, not a recipe tree or serialization size. Its fixed-operand witness does not repeatedly square a growing object. Its scalar witness traces an additional copy through ordinary operand promotion. Its repair changes condition joining while leaving the entire recipe representation in place. Even a perfectly shared recipe graph would not, by itself, prevent \code{seriesBinary} from constructing the repeated predicate list.

P08's broad suggestion to profile proof and normalization calls is also not a substitute for this repair. The defect is not merely that a theorem prover is slow on a hard condition; the input condition is repeatedly enlarged with logically redundant material. The earlier Mathics sign/realness recursion finding likewise has a different source mechanism and engine scope. CG-01 reproduces in Wolfram 15 without invoking that Mathics-only recursion.\cite{status,wave6}

The novelty ledger records these distinctions and its limitations. It also records rejected or duplicate candidates, without adding them to the article's findings count. In particular, the zero-order derivative cutoff issue and negative-source Gamma/Barnes power questions were excluded after matching prior reports. A suspected numerical source-domain bypass was refuted by following the public wrapper and running branch controls. The purpose of that ledger is to prevent a later intake from counting the same evidence twice, not to expand the issue total.

\section{Controls and the boundaries of the evidence}
\label{sec:controls}

\subsection{Ordinary observable comparisons}
A baseline screen used six functions,
\[
 1+x+x^2,\quad e^x,\quad\frac1{1-x},\quad\sin x,
 \quad\log(1+x),\quad\frac{x}{1+x},
\]
and seven observables of a formal variable $z$,
\[
 z^2,\quad z^{-1},\quad\sqrt z,\quad e^z,
 \quad\sin z,\quad\cos z,\quad\log z.
\]
The input expansions used package backend and cutoff four. For a returned ordinary series with numeric remainder power $0<P<20$, the comparison computed
\[
 \operatorname{Normal}\!\left(\operatorname{Series}
  \left[g(f(x))-\operatorname{Normal}(s_g),\{x,0,\lceil P\rceil-1\}\right]\right).
\]
This uses the returned \code{RemainderPower}, not an assumed property that might be absent. Forty-one of the 42 attempted combinations met the screen's admission test; none of those 41 produced a discrepancy. The original summarized response did not identify the one excluded combination, so the evidence file does not invent that information.

This screen is useful negative evidence, but not a proof of observable correctness. The oracle is native \code{Series}, and the screen is restricted to simple ordinary inputs. It was run on the unchanged baseline, not rerun as a complete screen after the candidate substitution. The supplied diagnostic runner records every combination explicitly and separates unassessed outputs and unavailable oracles from passes.

\subsection{Source-domain controls on inverse numerical evidence}
A source-level concern about an internal transformed-coordinate numerical helper disappeared when the public entry point was traced completely. The public \code{InverseNumericalCheck} applies a retained-source-domain check after the transformed helper returns.\cite{numericalwrapper,coordinate}

Two useful native controls used a source restriction $x>3$. For $f(x)=\exp(x^2)$, target $e^4$ corresponds to root two and was rejected as outside the branch; target $e^{16}$ returned root four. For $f(x)=\exp(x^2+x)$, the package used its \code{TargetLog} coordinate path: target $e^6$ was rejected, whereas $e^{20}$ returned root four. The latter approximation error was about $4.228\times10^{-9}$ at the tested cutoff and working precision.

These observations are retained as controls, not new defects or interval certificates. They also illustrate why inspecting a private helper without its public postconditions can produce a false positive. In the candidate work, the incompatible-domain control serves the same discipline: shrinking a condition expression is not acceptable if it stops rejecting contradictory input restrictions.

\subsection{Independent tests}
The final local Python run contains \textbf{26 passing unittest methods}. They cover exact recurrence models, semantic equivalence over finite Boolean assignments, scalar versus fixed-operand growth, opaque-clause treatment, and guarded transformation of transcribed source fixtures. Drift, duplicate definitions, reapplication and unrelated lookalike sites are tested separately.

These tests execute neither Wolfram Language nor Mathics. A Python model of conjunction is not an implementation test of a kernel's evaluator; a fixture replacement is not a full package build. Their value is narrower: they verify the reasoning model and that the patch tool refuses unexpected source shapes instead of silently performing a broad textual rewrite.

\subsection{What was not obtained}
No actual Mathics3 execution was available. No full upstream acceptance run, full staged modular integration, full staged standalone integration, replicated performance comparison or patched 41-case screen was completed. Several remote calls returned service or network errors; those failed calls are not counted as package failures. Only successful observations appear in the native ledger.

The distinction between a supplied regression script and an executed script is explicit throughout the bundle. The selected native mechanisms were exercised in submitted connector calls. The assembled \path{run_condition_probes.wl} and \path{run_observable_screen.wl} files are reproduction aids, not retrospectively manufactured run logs.

\section{Wolfram 15 and Mathics3: targeted portability analysis}
\label{sec:portability}
The reviewed loading path supplies a shared arithmetic implementation and isolates Mathics compatibility behavior in separate modules and contexts. Its compatibility layer includes association operations, scoped returns and bounded algebraic helpers; its numerical layer deliberately distinguishes unsupported high-precision reference solving from genuine numerical evidence. These are source-level observations, not a fresh claim that every public function is portable.\cite{mathicscompat,mathicsnumeric,loader}

CG-01 originates above those engine-specific details. The redundant conjunction is written in the ordinary shared binary engine, and scalar promotion also uses shared code. Thus the source concern applies to the Mathics path even though exact runtime multiplicities might differ because an evaluator or simplifier can canonicalize conditions differently.

The candidate helper uses ordinary structural operations: \code{Head}-based pattern dispatch through \code{And}, lists, one-level \code{Flatten}, \code{Join}, \code{DeleteDuplicates} and conjunction application. It does not require quantifier elimination, a native limit engine or an unimplemented numerical function. That keeps the portability obligation small, but it does not discharge it. Actual Mathics acceptance must still verify dispatch, exact structural comparison, preservation of distinct predicates, load/reload behavior and integration with the compatibility context.

\section{Focused implementation and development plan}
\label{sec:plan}

\subsection{Integrate the small source repair first}
Stage the complete candidate against \commit, inspect the two-site diff, and validate the ordinary arithmetic path before widening the change. The fixture tool intentionally refuses changed definitions and existing candidate helper names. If the source has moved, reconcile the patch with the actual code rather than weakening those guards.

The maintained modular source is the proper integration point. A standalone candidate is convenient for isolated testing, but the normal repository generation process should produce the eventual distribution file from the accepted modular change. Editing only the generated artifact would leave the source of truth divergent. This is an integration instruction for the supplied repair, not a new general build-system finding.

\subsection{Adopt an operational-condition invariant}
The narrowly useful development addition is an invariant at this boundary: repeated intersection of the same accepted conjunctive predicate must not increase its persistent occurrence count. Keep this invariant separate from the mathematical equality of finite expressions, remainder precision and refinement provenance.

Test scalar promotion explicitly. The failed merge-only candidate demonstrates that fixed independent operands alone are insufficient. Include fixed-left and fixed-right chains, scalar zero and one, nontrivial regular operands, and repeated shared domains. For each case compare expressions and remainder metadata in addition to counting predicate occurrences.

Distinct conditions require equally deliberate tests. Use different real parameter restrictions, incompatible restrictions, nested top-level conjunctions, duplicated disjunction clauses and formulas containing held subexpressions. The required behavior is exact duplicate removal, not a new logic solver or automatic weakening of branch predicates. A broad repository-wide replacement of every \code{And} would be unjustified.

\subsection{Measure the repaired boundary, not an unrelated aggregate}
The most diagnostic metric is the current domain's predicate multiplicity and leaf count. The full object size mixes operational metadata with histories, caches and other previously reviewed concerns. Keep those measurements separate so that unchanged recipe costs cannot conceal a successful condition repair, and recipe compaction cannot conceal a remaining condition defect.

For runtime measurements, compare identical package revisions apart from the candidate, the same neutral-operation chains, the same engine versions and the same evaluation settings. Use multiple fresh-session repetitions and report dispersion. Do not infer a speedup from the unreplicated baseline timing table in this article. An initially small exact expression is intentional: it minimizes confounding from coefficient growth.

This plan does not re-propose a shared provenance graph, global memoization, a new capability API, multivariate transseries or a general resource-budget redesign. Those are already part of the review baseline. The incremental development opportunity here is smaller and directly testable: make operational condition intersection idempotent in representation as well as in logic.

\section{Final assessment}
A neutral arithmetic operation should preserve not only the mathematical result but also a manageable representation of its unchanged validity conditions. At the reviewed revision, that operational contract fails: condition ownership is obscured by alignment, the left conditions are merged twice, and scalar promotion duplicates the current condition set again.

The result is unusually easy to isolate. The unchanged answer is the exact one-term function $x$. The observed current-domain counts follow the source-derived exponential recurrences exactly. The first plausible repair is demonstrably insufficient on scalar input. The stronger repair has a short Boolean correctness argument and successful focused Wolfram observations, including preservation and rejection controls for parameter domains.

That combination supports integrating and testing the local candidate. It does not justify relabeling existing backlog entries as new discoveries, declaring the entire repository correct, or claiming Mathics validation that did not occur. The useful deliverable is the specific new invariant, its public witnesses, its bounded repair mechanism, and an explicit path from the current focused evidence to two-engine acceptance.
