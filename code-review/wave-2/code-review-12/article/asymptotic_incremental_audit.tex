\section{Executive assessment}

\subsection{Recommendation}
Treat the next stabilization step as a repair of \emph{proof boundaries}, not an expansion of the feature list. The package is useful precisely because it carries more than a finite formula: it records asymptotic scales, remainders, source equations, branch conditions, and selected verification evidence. A defect that changes the truth of those annotations is more consequential than a missing expansion family. The strongest result here is an explicit certificate claiming that the root 2 satisfies the retained source condition \(x>100\). That claim is false, even though the unrestricted equation \(x=2\) has been solved correctly.

The other two findings concern information crossing representation boundaries. In N02, a syntactic exactness check admits a nonreal \code{Root}; truncation hides that coefficient, and a real-only inequality is then applied to the entire unknown function. In N03, a mathematically valid sparse series is exported to a native representation whose integer specifications cannot encode it. Both are small-input examples. Neither requires a large allocation, a pathological approximation threshold, or an untested conjecture about asymptotic behavior.

\subsection{Positioning relative to Wolfram Language}
The right description is a specialized, inspectable generalized-series and inverse-expansion layer built \emph{with} Wolfram Language. It is not a substitute for the host's complete asymptotic system. Native \code{Series}, \code{InverseSeries}, \code{ComposeSeries}, \code{Asymptotic}, and \code{AsymptoticSolve} already cover substantial parts of the domain. The repository adds selected sparse representations, inverse algorithms, explicit remainder transport, retained exact cores, and branch-aware workflows. Its special-function adapter itself consumes native series output.\cite{wl-series,wl-inverseseries,wl-compose,wl-asymptotic,wl-asymptoticsolve,repo-native,repo-readme}

Two direct comparisons illustrate why claims of uniqueness need care. For \(x+x^3\), native reversion and the package return the same finite inverse polynomial. For \(\zeta(x)\) at positive infinity, native \code{Asymptotic} and the package both return the first four Dirichlet terms. The package's explicit tail representation and additional bound metadata are useful, but the finite expansion is not beyond the native system. No speed advantage was measured in this audit.

\subsection{Evidence classes and limits}
\textbf{Observed native behavior} means an output was returned by the connected Wolfram evaluator for the pinned package or a stated focused modification. \textbf{Mathematical deductions} are the proofs in this article, including the trigonometric growth contradiction and the native-grid index calculation. \textbf{Source deductions} identify the inspected route responsible for a behavior. \textbf{Candidate designs} are proposed changes, not claims about code already present.

The archive contains 23 executed independent Python checks covering exact arithmetic facts, grid specifications, and patch-transformation fixtures. They passed. They are not an implementation of Wolfram evaluation, a substitute for native tests, or evidence that every package module works. The supplied eight-test Wolfram regression file and its runner were lexically checked for balanced delimiters, but were not executed as a complete file. Individual probes corresponding to its central contracts were executed separately. The combined patch was not run against the upstream suite.

This audit did not clone and test every repository artifact locally, prove all modules correct, or read every historical report line by line. Source inspection concentrated on the main kernel, certificates, ordinary and envelope arithmetic, source/domain transport, native and selected specialized forward paths, and supporting inverse/flat/Fourier modules. Appendix~\ref{sec:coverage} identifies that coverage. These limits matter: three concrete defects do not imply that unrelated numerical formulas are wrong, and passing controls do not prove the absence of other defects.

\section{Architecture and comparison with built-in capabilities}\label{sec:comparison}

\subsection{The ordinary mathematical representation}
The ordinary engine uses a positive local coordinate \(w\to0^+\) and sparse blocks
\[
 w^\beta P(\log w),\qquad \beta\in\RR,
\]
with exact admissible weights and polynomial logarithmic coefficients. Finite and infinite endpoints are reduced to coordinates such as \(x-x_0\), \(x_0-x\), \(1/x\), or \(-1/x\). Internally a jet consists of retained rows and a precision pair:
\[
 J=(T,\rho,d),\qquad
 f(w)=\sum_{(\beta,P)\in T}w^\beta P(\log w)
       +\OO\!\left(w^\rho(1+|\log w|)^d\right).
\]
An exact jet uses \(\rho=\infty\). The public \code{GeneralizedSeries} wrapper can additionally carry an offset, exact prefactor, source equation, conditions, operation recipe, and specialized scale information. \code{Normal} returns the finite expression, deliberately discarding the remainder contract.\cite{repo-main,repo-operations,repo-readme}

For ordinary inversion, the forward model is normalized to
\[
 f(u)=y_0+a u^p\left(1+\sum_{j=1}^{m}u^{\delta_j}P_j(\log u)\right),
 \qquad \delta_j>0.
\]
The inversion works in a positive target uniformizer and groups equal total weights. This avoids pretending that an arbitrary exact real support fits a single rational lattice. The package exposes coefficient-level access and retained inverse computations in addition to finite expressions. Those are meaningful interfaces for research workflows that repeatedly extend or inspect an inverse expansion.\cite{repo-main,repo-operations}

The representation also makes the proof obligations unusually visible. Addition and multiplication must transport both input errors; exponentiation needs a vanishing absolute error; logarithms need an appropriate positive leading approximation and relative error; derivatives require derivative information about the remainder. Merely differentiating or composing a finite expression would not establish those contracts. The inspected implementation already contains substantial machinery for these distinctions.\cite{repo-operations,repo-envelope,repo-arithmetic}

\subsection{Selected extensions, not a universal transseries field}
The repository has separate routes for logarithmic and source-coordinate reductions, exact-core perturbations, finite flat sectors, logarithmic Fourier coefficients, and Gamma/Barnes inverse scales. Its forward special-function support includes native-series import and dedicated parameterized or defining-sum paths. The README explicitly describes endpoint-specific admitted cases rather than support for every parameter regime of every named function.\cite{repo-readme,repo-sourcecharts,repo-flat,repo-fourier,repo-native,repo-dirichlet}

This division is sensible. A finite flat-sector calculation has an exponential degree and an inner algebraic precision; an ordinary power--log cutoff does not specify both. An oscillatory coefficient can be bounded without being nonzero, so it cannot automatically support division. A retained exponential prefactor can be exact while its correction bracket is only asymptotic. A single generic term count cannot erase these distinctions. The current specialized representations preserve important information that a finite expanded expression alone would lose.\cite{repo-flat,repo-fourier,repo-native,repo-gammaforward}

The same division creates interfaces worth auditing: a specialized result may later enter ordinary arithmetic or an envelope fallback. N02 concerns precisely such a fallback, although its input is a simple ordinary forward series. N03 concerns the opposite direction: converting a sparse representation into a more restrictive native view. The arithmetic formulas inside either representation can be correct while the bridge between their contracts is not.

\subsection{Executed overlap: polynomial inversion}
Experiment E11 compared
\begin{lstlisting}
s = AsymptoticInverse[x + x^3, {x, 0}, {y, 6}];
n = InverseSeries[Series[x + x^3, {x, 0, 6}], y];
{Normal[s], Normal[n], Simplify[Normal[s] - Normal[n]]}
\end{lstlisting}
and returned
\[
 \{y-y^3+3y^5,\quad y-y^3+3y^5,\quad 0\}.
\]
The package remainder was \code{PowerLogRemainder[y,7,0]}. This is a useful control for the core implementation and a warning against marketing ordinary reversion as absent from the host. It does not test every inverse method or prove equality of internal algorithms.

\subsection{Executed overlap: a Dirichlet scale}
Experiment E12 compared
\begin{lstlisting}
AsymptoticExpansion[Zeta[x], x -> Infinity, SeriesTermGoal -> 4]
Asymptotic[Zeta[x], x -> Infinity, SeriesTermGoal -> 4]
\end{lstlisting}
Both finite expressions were
\[
 1+2^{-x}+3^{-x}+4^{-x}.
\]
The package's stored remainder was
\[
 \code{PowerLogRemainder}[e^{-x},\log 5,0],
\]
which denotes an \(\OO(5^{-x})\) tail. Its dedicated Dirichlet path additionally records a first-omitted-integer bound. For fixed integer \(m\ge1\) and \(S>1\), monotone integral comparison gives
\begin{equation}\label{eq:zeta-tail}
 m^{-S}\le\sum_{n=m}^{\infty}n^{-S}
 \le m^{-S}+\int_m^\infty t^{-S}\,dt
 =m^{-S}\left(1+\frac{m}{S-1}\right).
\end{equation}
This is the bound implemented in the inspected source. It is useful explicit information, but the calculation above is not a new algorithm contributed by this audit.\cite{repo-dirichlet}

The correct comparative statement is therefore precise: in this tested case the finite terms agree, while the package offers a particular persistent remainder/bound interface. A comparison against \code{Series} alone would miss native \code{Asymptotic}'s ability to return the same exponential scale.

\finding{N01}{Ambient assumptions can invalidate a positive certificate}\label{sec:n01}
\textbf{Priority: high. Evidence: native public counterexample and focused repair controls.}

\subsection{The counterexample}
Construct an inverse object in a clean assumption context:
\begin{lstlisting}
s = Block[{$Assumptions = True},
  AsymptoticInverse[
    ConditionalExpression[x, x > 100],
    {x, Infinity}, {y, 2}]];
\end{lstlisting}
This describes the identity function on the retained source domain \(x>100\), approached at positive infinity. The saved object retains \code{Function -> x}, \code{Expression -> y}, and \code{SourceDomain -> x > 100}. The following requested interval is deliberately outside that domain:
\begin{lstlisting}
Block[{$Assumptions = True},
 InverseCertificate[s, 2,
   "Interval" -> {1, 3}, "Center" -> 2,
   "MaxRefinements" -> 0]]
\end{lstlisting}
The clean-context output is correctly \code{Failure["OutsideBranch",...]} with the source-domain condition unproved over the entire closed interval.

Now change only the caller's ambient assumptions, not the saved object, target, center, or interval:
\begin{lstlisting}
Block[{$Assumptions = x > 100},
 InverseCertificate[s, 2,
   "Interval" -> {1, 3}, "Center" -> 2,
   "MaxRefinements" -> 0]]
\end{lstlisting}
\Needspace{10\baselineskip}
The native output includes
\begin{lstlisting}
<|"Certified" -> True,
  "RootEnclosure" -> {2, 2},
  "CertifiedSourceDomain" -> x > 100,
  "SourceDomainVerified" -> True,
  "CertifiedTarget" -> 2,
  "ExistenceEvidence" -> "Residual bracket containment", ...|>
\end{lstlisting}
This is not merely a misleading numerical name or an overly broad reading of a local theorem. The output explicitly says that the retained source domain was verified. Every point in \([1,3]\) violates \(x>100\), and in particular the alleged root does. Experiment E02 records the result; E10 reconfirms it alongside the numerical-check control.

\subsection{What is correct, and what is false}
The unrestricted identity equation has root 2. Its derivative is 1 and its center residual is zero. Thus the rational interval arithmetic has an easy, correct equation-solving problem. The error is in the additional domain proposition attached to that solution.

\begin{proposition}
Let \(D(x)\) be the retained source condition and \(I\) the verification interval. A certificate claiming a unique root of the restricted source in \(I\) must establish the relevant domain obligation, here \(\forall x\in I\,D(x)\), from the recorded premises. Assuming \(D(x)\) during that check does not establish the obligation.
\end{proposition}
\begin{proof}
For this example take \(D(x)\equiv x>100\) and \(I=[1,3]\). The quantified domain obligation is false, independently of the identity equation. Simplifying \(D(x)\) under premise \(D(x)\) proves only the tautology \(D(x)\Rightarrow D(x)\), not that the interval lies in the domain. The returned root 2 therefore cannot satisfy the claimed restricted-source certificate.
\end{proof}

The package's own scope text promises a root on the selected source side and within retained source-domain conditions. N01 contradicts that promise on a public path; it does not demand a global inverse theorem that the implementation never offered.\cite{repo-cert}

\subsection{Root cause: positional assumptions are not isolation}
The inspected certificate helper \code{certPositiveCondition} begins by refining a predicate under a positional reality assumption for the source variable. The critical operation has the shape
\begin{lstlisting}
Refine[condition, Element[x, Reals]]
\end{lstlisting}
That form does not neutralize \code{$Assumptions}. Wolfram documents that the default \code{Assumptions} option is appended to the positional assumptions; explicitly supplying the option prevents that default contribution.\cite{wl-refine}

Experiment E01 directly observed
\begin{lstlisting}
Block[{$Assumptions = True},
 Refine[x > 100, Element[x, Reals]]]       (* x > 100 *)
Block[{$Assumptions = x > 100},
 Refine[x > 100, Element[x, Reals]]]       (* True *)
\end{lstlisting}
Once the condition becomes \code{True}, the later interval test no longer has the original inequality to verify. The exact residual and derivative computations cannot recover the lost obligation.

This is a stronger consequence than the old observation that construction could use ambient assumptions while recording \code{Assumptions -> True}. Here the object was constructed before the problematic ambient assumption was introduced. Fixing constructor metadata alone would leave this verification-time counterexample intact.\cite{review8,repo-status}

\subsection{A revealing differential control}
Under the same ambient assumption, the numerical checker rejects target 2:
\begin{lstlisting}
Block[{$Assumptions = x > 100},
 InverseNumericalCheck[s, 2, WorkingPrecision -> 20]]
(* Failure["OutsideBranch", ...] *)
\end{lstlisting}
It substitutes the recovered numerical root into the source condition and recognizes the failure. Thus the certificate, which makes the stronger claim, accepts a case that the noncertifying numerical check rejects. This is not proof that the numerical route is generally sounder; it is an excellent targeted regression relation.\cite{repo-numerical}

\subsection{Focused repair and validation}
The candidate change isolates the entire public verification body:
\begin{lstlisting}
InverseCertificate[GeneralizedSeries[a_Association], yv_, opts___] :=
  catch[Block[{$Assumptions = True},
    Module[(* existing locals *),
      (* existing verification body *)]]]
\end{lstlisting}
The listing is schematic; the accompanying patch rules preserve the actual option pattern and body. Whole-body isolation is preferable to changing one visible \code{Refine}, because other simplification or branch-reduction helpers called during verification can otherwise consult the same ambient state. It is also preferable to copying \code{$Assumptions} into certificate metadata: recording an unjustified premise would not turn an empty-domain interval into a valid one.

Experiment E07 tested this focused modification. The target-2 case returned \code{OutsideBranch} under \code{$Assumptions = x > 100}. A positive control with target 102, interval \(\{101,103\}\), and center 102 still returned a positive certificate with enclosure \(\{102,102\}\). The repair did not simply disable all certification.

This is a narrow repair, not protection against arbitrary redefinition of Wolfram primitives or corruption of saved objects. It also cannot repair an object whose coefficients were already simplified under unrecorded assumptions during construction. Those are separate boundaries. The immediate claim is only that verification must not import fresh ambient assumptions as proofs of interval obligations.

\subsection{Acceptance criteria}
For a saved valid object and fixed exact target/interval, changing unrelated caller assumptions must not change the truth of its certificate. A source-domain predicate must remain an obligation until proved on the interval; it must not be a premise that discharges itself. Regression variants should include contradictory ambient assumptions, predicates involving the source variable, parameter-only assumptions, and calls from \code{Assuming}. Positive controls must remain available so that blanket rejection is not mistaken for correctness.

The package should distinguish two policies explicitly. During \emph{construction}, a documented policy may capture selected caller assumptions and store them with the result. During \emph{verification}, the already recorded premises are the input; any additional source-domain predicate is a proposition to prove. Mixing these policies is the essential error, not the mere presence of a global Wolfram variable.

\finding{N02}{Nonreal admission followed by a false real-only error transport}\label{sec:n02}
\textbf{Priority: high. Evidence: native public path and a mathematical contradiction.}

\subsection{An exact coefficient without an explicit complex literal}
Set
\begin{lstlisting}
c = Root[5 + 5*# + #^5 &, 2];
{Head[c], FreeQ[c, _Real | _Complex], Element[c, Reals]}
(* {Root, True, False} *)
\end{lstlisting}
The exact algebraic number is nonreal, but its expression tree has no machine-real or \code{Complex} literal. The tested numerical value was approximately
\[
 c=-0.8026283840948295-1.1850818593889156\,i.
\]
The approximation is illustrative; the exact \code{Element[c,Reals] -> False} observation is what matters.

There is also a simple algebraic explanation. The polynomial \(p(t)=t^5+5t+5\) is irreducible by Eisenstein's criterion at 5. For real \(t\),
\[
 p'(t)=5(t^4+1)>0,
\]
and \(p(-1)<0<p(0)\). It therefore has exactly one real root. Wolfram's documented ordering puts real roots first; index 2 is consequently nonreal.\cite{wl-root}

The current helper \code{exactQ} checks absence of \code{_Real | _Complex}. That is an exactness/encoding check, not a semantic proof of reality. The public validation message speaks of exact real input, but the ordinary constant admission route does not consistently establish that stronger property.\cite{repo-main}

\subsection{The public calculation}
The first operation deliberately discards the coefficient into a remainder:
\begin{lstlisting}
s = AsymptoticExpansion[c/x, {x, 0, -2}];
\end{lstlisting}
The finite support below the exclusive cutoff \(-2\) is empty. The returned object includes
\begin{lstlisting}
"Expression" -> 0
"Remainder" -> PowerLogRemainder[x, -1, 0]
"TargetDomain" -> x > 0
\end{lstlisting}
Its original source is still \(c/x\). Consider now the ordinary public operation
\begin{lstlisting}
t = Sin[s];
\end{lstlisting}
Experiment E04 returned a composite object with
\begin{lstlisting}
"Expression" -> 0
"Remainder" -> PowerLogRemainder[x, -1, 0]
"RemainderScaleExpression" -> x^(-1)
"Scale" -> "Composite"
\end{lstlisting}
and the composite majorant contract asserting that the represented function differs from the finite expression by the recorded asymptotic envelope.

The initial magnitude statement \(c/x=\OO(1/x)\) would be valid even in a complex-valued interpretation. The false step is the conclusion that \(\sin(c/x)=\OO(1/x)\). This makes N02 stronger than a complaint that the implementation has violated its advertised real-only API: the returned bound is not rescued by allowing complex values.

\subsection{Proof that the remainder is wrong}
\begin{proposition}\label{prop:sin}
For every fixed \(c=a+ib\) with \(a,b\in\RR\) and \(b\ne0\),
\[
 \sin(c/x)\notin\OO(1/x)\qquad(x\to0^+).
\]
\end{proposition}
\begin{proof}
The elementary identity for the complex sine gives
\[
 |\sin(a/x+ib/x)|^2
 =\sin^2(a/x)+\sinh^2(b/x).
\]
Hence
\[
 x\,|\sin(c/x)|\ge x\sinh(|b|/x).
\]
Writing \(t=|b|/x\), the right-hand side is \(|b|\sinh(t)/t\), which tends to infinity. Thus no fixed constant can bound \(|\sin(c/x)|\) by a multiple of \(1/x\) near zero.
\end{proof}

No delicate cancellation or high-order coefficient computation is involved. The counterexample consists of one algebraic coefficient, one monomial, one truncation, and one unary observable. It exposes a missing premise of an otherwise valid real inequality.

\subsection{Source path and the lost information}
In the ordinary forward engine, an expression independent of the local variable enters \code{pConst}. The inspected definition verifies polynomial dependence on the logarithm placeholder and performs zero handling; it does not require every admitted coefficient to be real. Consequently the nonreal \code{Root} reaches the jet.\cite{repo-main}

After truncation, the known finite expression is 0. The ordinary unary route cannot treat the unbounded remainder as a small Taylor increment and uses the allowed envelope fallback. There, \code{seriesEnvelopeUnary} checks that the \emph{finite approximation} is real. For \code{Sin} and \code{Cos}, it then preserves the error using their real-line Lipschitz property. The reality of the unknown represented function, rather than just 0, has not been established.\cite{repo-arithmetic,repo-envelope}

The logical distinction is
\[
 \operatorname{Expression}(s)\in\RR
 \quad\not\Rightarrow\quad
 \operatorname{Realization}(s)\subseteq\RR.
\]
A pure remainder has no retained coefficient from which its codomain can be recovered. Truncation must not erase a condition needed by later operations. Checking only surviving rows is therefore intrinsically insufficient, even if that check is implemented perfectly.

This sharpens review 7's F04, which identified the missing realness gate and proposed a symbolic logarithm test, and the related concern that unknown remainders cannot inherit properties from finite approximations. The present example is native, uses an exact numeric coefficient, reaches a public arithmetic operation, and has a proved false output bound.\cite{review7,repo-status}

\subsection{A focused guard, with its compatibility caveat}
The supplied candidate inserts a semantic check in \code{pConst}:
\begin{lstlisting}
If[! And @@ (
   TrueQ[Refine[Element[#, Reals], ass, Assumptions -> True]] & /@
     CoefficientList[c, ell]),
 fail["UnprovedRealCoefficient",
   "Every admitted coefficient must be real under the explicit assumptions.",
   <|"Coefficient" -> c|>]];
\end{lstlisting}
The explicit option prevents the guard from silently accepting fresh ambient assumptions. Experiment E08 applied the equivalent guard to the fully qualified private definition. The nonreal \code{Root} source was rejected with \code{UnprovedRealCoefficient}. Ordinary \(e^x\) still produced \(1+x+x^2/2\), and \(a x\) with explicit \(a\in\RR\) assumptions was accepted.

This is a \emph{guard demonstrator}, not a complete semantic-domain implementation. A strict check can reject formerly accepted symbolic coefficients unless their realness is explicitly provable. Specialized algorithms may use complex intermediate expressions before a justified real projection, so placing a universal realness requirement in every low-level algebra would be too crude. The intended invariant must be attached to the particular real coefficient algebra, not imposed indiscriminately on the Fourier or native complex-amplitude machinery. The archive does not claim that the combined guard has passed all those paths.

A production repair should decide where the strict real contract is established, then audit every constructor and adapter that can create an object consumed by the real-only envelope rules. It should not repair this example by inspecting the discarded \code{FrontierTerm} alone: future errors may originate from an unknown tail rather than one visible coefficient.

\subsection{Whole-germ codomain evidence}
A useful next contract is a small, explicit classification such as
\begin{lstlisting}
"ValueDomain" -> "Real"
"ValueDomainEvidence" -> <|
  "Scope" -> "WholeRepresentedGerm",
  "Assumptions" -> recordedAssumptions,
  "Source" -> admissionOrTransportRecord|>
\end{lstlisting}
This is a proposed design, not an existing property. The key phrase is \emph{whole represented germ}. Exact real arithmetic preserves it; certified real unary maps can preserve it; truncation preserves it because truncation changes available approximation data, not the underlying function. Unknown or complex codomain must not be silently upgraded because a finite expression happens to become real.

For a real germ \(f=e+r\), the inequality
\[
 |\sin f-\sin e|\le |r|
\]
is valid without requiring \(r\to0\). That explains why the existing fallback is valuable and should not simply be deleted. For a general complex germ it is invalid; a different estimate involving imaginary parts or a controlled complex neighborhood is required. The simplest supported policy is to reject the real-only transport when whole-germ reality is absent. General complex support is a separate existing roadmap topic, not a necessary precondition for fixing N02.

\finding{N03}{Native index range is independent of sparse support size}\label{sec:n03}
\textbf{Priority: medium. Evidence: native public examples and tested conversion preflight.}

\subsection{What the earlier repair already accomplished}
The current \code{makeRationalSeriesData} computes a rational exponent lattice, limits the retained coefficient span to 100,000 slots, and does not pad the coefficient list all the way to the remainder index. That addresses the earlier eager-dense-allocation problem. This audit does not repeat the old allocation example as though the repair were absent.\cite{repo-main,repo-status,review7,review8}

There is a separate target-format restriction. A native \code{SeriesData} object has integer start and remainder specifications and a positive integer power denominator. The successful native diagnostic probes reported that these specifications must be machine-sized integers. A tiny sparse support can require a large value in one of those fields even when its coefficient list has length one.

\subsection{Two one-slot examples}
Let
\[
 Q=2^{100}=1267650600228229401496703205376.
\]
First compute
\begin{lstlisting}
a = AsymptoticExpansion[1 + x^Q, {x, 0, 2}];
\end{lstlisting}
The finite part is 1. The exact first omitted monomial supplies remainder exponent \(Q\), even though the requested cutoff was only 2. The optional native view has the specification
\begin{lstlisting}
SeriesData[x, 0, {1}, 0, Q, 1]
\end{lstlisting}
with one coefficient. The remainder index is outside the tested native machine-integer range.

Second compute
\begin{lstlisting}
b = AsymptoticExpansion[
  x^(1/Q) + x^(3/Q), {x, 0, 2/Q}];
\end{lstlisting}
The finite part is \(x^{1/Q}\), and the remainder exponent is \(3/Q\). The native index triple is \(\{1,3,Q\}\). Again there is one retained slot, but now the denominator is not representable.

Experiment E06 observed both public objects retaining invalid native \code{SeriesData} forms instead of a structured unavailable-view result. Separate direct native probes E05 emitted \code{SeriesData::sdatn} for oversized order specifications and \code{SeriesData::sdatd} for an oversized denominator. A large starting index was also checked directly. No large array was allocated to demonstrate any of these failures.

\subsection{The precise conversion obligation}
For retained rational exponents \(S\) and rational remainder exponent \(\rho\), define
\[
 d=\operatorname{lcm}\{\operatorname{den}(\beta):\beta\in S\cup\{\rho\}\},
 \quad n_{\min}=d\min S,\quad n_{\max}=d\rho.
\]
For nonempty \(S\), the retained dense span is
\[
 N_{\rm slots}=d\max S-n_{\min}+1.
\]
The empty-support case has no coefficient slots and a separately chosen starting index. These are the quantities calculated by the inspected helper.\cite{repo-main}

The first witness has
\[
 (n_{\min},n_{\max},d,N_{\rm slots})=(0,Q,1,1),
\]
and the second has
\[
 (n_{\min},n_{\max},d,N_{\rm slots})=(1,3,Q,1).
\]
A condition on \(N_{\rm slots}\) cannot imply a bound on \(n_{\max}\) or \(d\). Nor does a small requested cutoff imply a small exact first-omitted exponent. The density cap and the integer-range preflight address logically independent properties.

\subsection{Impact and severity}
The sparse finite expression and its custom remainder remain mathematically useful. This finding does not establish incorrect coefficients in the main expansion. The failure is that an \emph{optional} native view can emit an error or remain an invalid expression while the constructor is otherwise succeeding. Callers using \code{Check}, expecting a usable \code{SeriesData} property, or forwarding that property to native operations can be disrupted by information they never needed for the sparse computation.

This is why a medium priority is appropriate rather than labeling it another high-severity allocation defect. The old density repair removed the large temporary array risk in these one-slot cases. What remains is a reproducible representability and API-totality gap at the adapter boundary.

\subsection{Focused range guard}
Before allocating or constructing the native view, the candidate checks all three indices against the runtime signed machine-integer interval:
\begin{lstlisting}
If[! And @@ (
    IntegerQ[#] &&
      -2^($SystemWordLength - 1) <= # < 2^($SystemWordLength - 1) & /@
        {nmin, nmax, den}) || den <= 0,
 Return[Missing["NativeSeriesDataIndexRange",
   <|"Indices" -> {nmin, nmax, den},
     "SystemWordLength" -> $SystemWordLength|>], Module]];
\end{lstlisting}
This leaves the sparse object intact and makes the unavailable conversion explicit. The diagnostic separates an index-range refusal from the existing density refusal; the two should not share a misleading failure label.

Experiment E09 applied the source insertion to a downloaded standalone, wrote a temporary patched file, and loaded it with \code{Get}. On the 64-bit native kernel, both witnesses returned an unavailable-view \code{Missing} value identifying the out-of-range index. Their finite parts were unchanged. The ordinary \(e^x\) control retained a valid native view:
\begin{lstlisting}
SeriesData[x, 0, {1, 1, 1/2}, 0, 3, 1]
\end{lstlisting}
The guard has not been certified on every platform or at every extreme accepted by the host representation. Boundary regressions should include the smallest and largest machine-sized values, negative starting orders, empty support, ordinary ramification, and safe refusal of large denominators.

\subsection{Performance implication beyond this example}
A representation adapter needs at least three independent preflights: mathematical representability in the target scale, resource feasibility of the target coefficient layout, and representability of the target's metadata integers. Counting terms alone addresses none of these completely. That statement is not a call to repeat the earlier broad resource-budget recommendations; it specifies the missing native-view test exposed by N03.

The bit length of an exponent is a different input dimension from the number of nonzero blocks. A useful targeted benchmark varies those dimensions independently: hold support size at one while increasing the remainder index; hold the lattice span at one while increasing the denominator; then hold indices small while widening interior gaps. Record whether conversion succeeds, is refused cleanly, or emits messages. This experiment measures adapter behavior, not inverse-coefficient speed, and can be bounded before any large allocation.

\section{A development plan derived from the counterexamples}\label{sec:plan}

\subsection{First milestone: make verification context-independent}
The immediate task is to isolate \code{InverseCertificate} from fresh ambient assumptions and add the invalid-interval/valid-interval pair. Its completion criterion is specific: E02 must reject the false domain, E07's valid root must still certify, and E10's numerical-domain rejection must no longer disagree with a positive certificate on that case.

The next inspection target is every helper called by the certificate that simplifies a condition before substituting an interval or a target. Classify each condition as a recorded parameter premise, a source-domain obligation, an interval-containment fact, or a conclusion. The categories should not be collapsed into one conjunction passed indiscriminately to a simplifier. In particular, the condition being verified must not enter the premise set merely because it appears in \code{$Assumptions}.

A useful design rule is
\[
 \operatorname{Verify}(\text{saved data},\text{request};A_{\rm ambient})
 =\operatorname{Verify}(\text{saved data},\text{request};\mathrm{True})
\]
for all caller contexts that do not change the explicit arguments themselves. This is a proposed noninterference property, not a claim that Wolfram evaluation is immune to arbitrary symbol definitions. It is deliberately narrower and testable.

Saved objects can contain legitimate parameter assumptions. The checker should use those as recorded conditional premises, or require parameters to be instantiated when the interval evaluator needs numeric constants. It should not erase legitimate recorded information while blocking external context. Conversely, a condition involving the interval variable is not a numerical parameter fact and generally must be verified throughout the interval. These distinctions are the added engineering requirement beyond the old recommendation to retain assumption metadata.

\subsection{Second milestone: establish a real-germ boundary}
The immediate N02 guard closes the demonstrated ordinary coefficient route. The durable task is to define where realness is proved for every object accepted by real-only arithmetic. That proof must concern the exact source or the allowed unknown remainder, not only the visible approximation. A constructor that cannot establish its promised real domain should fail or return an explicitly weaker object that real-only operators refuse.

For native special-function import, the implementation already contains deliberate real-source and real-projection checks. Those should supply codomain evidence rather than forcing later consumers to guess from the simplified finite output. For flat or Fourier calculations, complex intermediate coefficients can be compatible with a real final germ when the relevant symmetry or projection is established. The proposal is therefore not ``reject every occurrence of \(i\) anywhere.'' It is ``require the real-only transport to consume a justified real-germ contract.''\cite{repo-native,repo-fourier}

The minimum propagation rules are uncomplicated. Real constants and the positive real local variable establish realness. Real addition and multiplication preserve it. A real logarithm needs positive input; a noninteger power needs its specified real branch. Truncation preserves previously established whole-germ realness but cannot establish it anew. A bounded real observable can then use the correct real inequality. Any native or specialized operation that cannot justify the flag must return unknown rather than defaulting to real.

Acceptance should include all three shapes: a real finite approximation with a real remainder, a real finite approximation with a nonreal discarded contribution, and a complex intermediate representation whose final source is proved real. Only the second must be excluded from the real Lipschitz rule; the first is useful supported behavior, and the third prevents an unnecessarily destructive patch.

\subsection{Third milestone: make the native view independently fallible}
The N03 preflight should return a reasoned unavailable-view value without changing \code{Normal[s]}, the custom remainder, or the sparse coefficients. The practical invariant is
\[
 \text{successful sparse construction}
 \not\Rightarrow \text{successful native conversion},
\]
while failure of optional conversion must not silently become failure of the sparse mathematics.

The view should distinguish irrational support, excessive retained lattice span, out-of-range indices, and other semantic limitations rather than exposing an unevaluated invalid \code{SeriesData}. The first two categories already have explicit handling in the inspected helper; the new change supplies the third. A completely lazy export interface may remain desirable, but that was already discussed in earlier reviews. N03 does not require waiting for that larger redesign.\cite{repo-main,review7,review8}

For API consumers, an unavailable view is not a numerical or mathematical failure. Document that native consumers must check for a usable \code{SeriesData} value; custom-series consumers should continue using the original object. The failed conversion's diagnostic should state which metadata field cannot be represented and leave the original exact value available for inspection.

\subsection{A compact regression matrix}
The three defects suggest paired tests that ordinary example-by-example output checks miss:
\begin{longtable}{@{}P{0.20\textwidth}P{0.34\textwidth}P{0.38\textwidth}@{}}

\toprule Boundary & Paired experiment & Required invariant\\\midrule\endhead
Verification context & Same saved inverse and interval; clean versus source-dependent ambient assumptions & The domain certificate must not change from false to true.\\
Coefficient encoding & Explicit nonreal constant versus nonreal algebraic \code{Root} & Semantic nonreality cannot be accepted merely because one encoding lacks \code{Complex}.\\
Truncation & Same realness evidence before and after all finite rows are dropped & The whole-germ codomain is preserved or remains unknown; it is not inferred from zero.\\

\end{longtable}

The archive's eight desired-contract tests cover the minimal examples and positive controls, not every row of this extended matrix. The matrix is a concrete follow-on testing specification, not a statement of tests already run. It can be applied to both modular and standalone loading so that a correct kernel change is not lost during distribution regeneration.

\subsection{Performance work should preserve these proof obligations}
The proposed changes add different costs. Certificate isolation is a context boundary, not another asymptotic coefficient algorithm. Native index preflight is small integer arithmetic done before allocation. Semantic coefficient admission can be expensive when a symbolic realness question is difficult. That last cost needs a documented policy: accept a proved result, reject a disproved result, and distinguish unresolved or budget-exhausted proof attempts from mathematical nonreality.

A cache for realness or domain results must include the complete relevant assumptions and expression, and must not reuse a result proved under a stronger context as though it were unconditional. This is not a general recommendation to add more caches; it is a restriction any optimization of the new semantic checks must satisfy. Caching a \code{True} answer without its premises would recreate N01 in a different form.

For the same reason, performance measurements should report which proof obligations were discharged, not only elapsed time and the number of retained terms. A faster result produced by skipping a domain check is not an equivalent benchmark. A refusal caused by an undecided proof is also different from an algorithm running out of coefficient budget. No performance numbers for these repairs are claimed here; the native checks established behavior, not comparative speed.

\section{What this audit does not add to the backlog}\label{sec:excluded}

\subsection{Known issues that are not new findings here}
The consolidated status already covers multiple precision, refinement, resource, API, distribution, and future-feature topics. Repeating that list would increase the apparent breadth of this article without adding evidence. In particular, this audit does not claim a new general logarithmic-tail defect, a new generic \code{MaxTerms} bypass, a new whole-suite infrastructure gap, or a new need for complex/multivariate transseries. Those issues have existing homes.\cite{repo-status}

The source-level concern about the old \code{fwdSeries} fallback's unseen logarithmic tail was inspected, but no new public wrong-bound example was established here. It remains a previously recorded issue, not a fourth finding. Likewise, source-domain transport through arbitrary series composition deserves careful treatment, but the current article's confirmed domain counterexample is specifically the certificate path. These distinctions prevent plausible risks from being presented as executed bugs.

\subsection{Corrections to overly broad assurances}
The earlier certificate discussion correctly explains residual and derivative enclosure mathematics and the intended interval-domain check. N01 shows that the existence of those checks in source is not sufficient to assert the implemented domain certificate is always enforced. The narrower statement is that the interval arithmetic supplies the stated conclusion \emph{provided the verification context cannot discharge a domain obligation by assuming it}. The counterexample supplies the missing qualification.\cite{review7,repo-cert}

Similarly, accepting a nonreal coefficient is not merely harmless extra generality outside a real-only specification. Once the object can reach a real-only bound, the omission has a false mathematical consequence. N02 supplies that consequence without depending on an exotic special-function expansion. Finally, the recent density guard should be credited rather than dismissed: N03's counterexample works precisely because coefficient storage is small and the remaining restriction is a different one.

\subsection{No unsupported generalization from the findings}
Nothing in these experiments establishes that ordinary inverse coefficients, the Gamma/Barnes expansions, or the explicit Dirichlet tail formula are generally wrong. The successful polynomial and zeta comparisons are controls, not broad validation. Likewise, the focus on certificate soundness does not convert an ordinary package review into a claim of security isolation against malicious kernel definitions. The required contract is mathematical reproducibility from explicit stored data within a normally functioning Wolfram environment.

A reasonable release decision is to fix these demonstrated paths, run the relevant and cross-cutting native tests, and retain a precise scope statement. It is not necessary to solve every previously listed research extension before providing a reliable specialized package. The distinction between an admitted answer with justified metadata and an honest unsupported result remains the right boundary.

\section{Artifact guide and reproducibility}\label{sec:artifacts}

\subsection{Files in the archive}
The article source and PDF are in \code{article/}. The machine-readable record \path{evidence/native_observations.json} contains selected successful outputs labeled E01--E12. It is explicitly a curated transcription, not a fabricated complete session log. The snapshot and novelty ledger are beside it. The Python test output is \code{evidence/python-checks.txt}.

The code directory contains a bounded native reproducer, eight desired-contract tests, a fail-closed test runner, and a guarded source-change emitter. The emitter reads the two affected canonical kernel files and verifies unique exact anchors before writing patched \emph{copies} to a new destination. When the input is a Git checkout, it also requires the expected revision. It does not alter the checkout, upload changes, or overwrite the standalone distribution.

\begin{lstlisting}

evidence/   Native excerpts, snapshot, novelty ledger, check output

\end{lstlisting}

\subsection{Run the native probes on an explicit local package}
Use a clean kernel and an independently obtained copy of the pinned package. The supplied runner never downloads or silently replaces that package:
\begin{lstlisting}
wolframscript -file code/reproduce.wl \
  /absolute/path/to/AsymptoticInverse.wl observations.json

wolframscript -file code/run_regressions.wl \
  /absolute/path/to/AsymptoticInverse.wl test-results.json
\end{lstlisting}
The first command records behavior, messages, kernel version, elapsed time, and a hash of the local file. It bounds each observation in time and memory. The second evaluates the desired contracts and returns a failing process status unless the expected test report is obtained with all eight tests passing. Some desired contracts are expected to fail on the pinned baseline; that is their purpose.

These delivered scripts were not run end to end through a local Wolfram executable in this environment. The successful observations were obtained as separate remote native calls. The distinction is preserved so that a user does not mistake the supplied files for a completed full regression report.

\subsection{Generate and review the candidate source changes}
\begin{lstlisting}
python code/apply_candidate_patch.py \
  /absolute/path/to/pinned-checkout \
  --output /absolute/path/to/new-candidate-directory
\end{lstlisting}
The output consists of modified copies, a unified diff, and a hash manifest. An unexpected source revision, missing anchor, duplicate anchor, or destination inside the checkout is refused. The rule file uses explicit source anchors rather than approximate regular-expression edits across unrelated definitions.

After reviewing and applying the canonical-source changes, regenerate the standalone with the repository's builder. Test both loading forms. Changing only the generated root file would leave the modular implementation inconsistent; changing only the modules without regeneration would leave the advertised standalone unchanged. That distribution relationship is already documented upstream.\cite{repo-readme}

The N01 and N03 focused source modifications were tested natively; N02's equivalent private guard was tested through a fully qualified redefinition. They were not tested together against the full package. In particular, the semantic realness guard needs coverage of parameter assumptions, special-function projections, and internal complex working representations before release qualification.

\subsection{Independent checks and article build}
\begin{lstlisting}
(cd code && python -m unittest test_independent -v)
make pdf
\end{lstlisting}
The 23 Python checks use standard-library exact rational and integer operations plus source-transformation fixtures. They verify the one-slot grid calculations, machine-range predicates, the identity-domain counterexample, elementary polynomial facts, and patch-anchor behavior. The divergence proof in Proposition~\ref{prop:sin}, not numerical sampling, establishes the false remainder. None of these tests executes Wolfram package code.

The article is built with pdfLaTeX and \code{latexmk}. All required LaTeX sources are included; no proprietary fonts or external figures are needed. The PDF was compiled and visually inspected after rendering. Build intermediates are omitted from the final archive.

\section{Conclusion}
The repository's strongest contribution is not just another list of asymptotic terms. It is an attempt to make specialized inverse expansions usable as objects with explicit mathematical obligations. This incremental audit identifies three places where those obligations are lost across boundaries: caller context becomes verification evidence, the finite approximation's codomain substitutes for the whole function's codomain, and sparse mathematical data are assumed to fit native integer specifications.

The counterexamples are deliberately small and decisive. The domain \(x>100\) does not contain root 2. A nonreal coefficient divided by \(x\) produces exponentially growing complex sine, not an \(\OO(1/x)\) remainder. A one-entry coefficient array does not make \(2^{100}\) a machine-sized integer. Each finding has a focused repair, a positive control, and a clear statement of what remains to be validated.

The resulting development recommendation is correspondingly narrow: isolate verification premises, preserve whole-germ semantic evidence, and make optional native conversion explicitly fallible. These changes strengthen the package's distinctive value without pretending to replace the broad native Wolfram asymptotic system or republishing the first nine reviews.
